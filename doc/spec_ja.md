## 1. 序文

### 1.1 目的

Lask は、タスクを関数として表現し、自動化と CI/CD 実行記述を一貫した言語で記述することを目的とする。
本仕様は、実装者・利用者・ツール開発者が同じ意味論を共有できるよう、構文・型・評価・入出力・観測性を規定する。

Lask の設計目標は次の通りである。

- 関数合成を中心に据えた宣言的な記述性
- 手続的記述に慣れた利用者でも段階的に導入できる可読性
- 実行前検証（構文・参照・型）による安全性
- 実行環境差異の吸収による再現性
- 実行ログ・トレースによる高い観測可能性

### 1.2 対象読者

本仕様の対象読者は次の通りである。

- 言語処理系（パーサ、型検査器、実行器）を実装する開発者
- CLI、LSP、REPL、ログ収集など周辺ツールを実装する開発者
- 言語仕様に準拠した運用ルールを設計する利用者・運用者

### 1.3 仕様のスコープ

本仕様は、以下を規定対象とする。

- 字句仕様、構文仕様、型システム
- 宣言・式・モジュール・制御構造
- 静的意味論と動的意味論
- CLI仕様、標準入出力、実行環境
- シリアル化規約、エラー体系、観測性（ログ/トレース/イベント）

### 1.4 非スコープ

以下は本仕様の規定対象外とする。

- 特定実装に依存する最適化方式
- 実装言語・ライブラリ選定
- 具体的な運用インフラ構成（クラウド製品、ミドルウェア選択）
- 組織固有のデプロイ手順や承認フロー
- 互換性・移行方針（`compatibility_ja.md` で規定する）

### 1.5 要求事項定義書との関係

`requirements_ja.md` は達成すべき要求を定義する上位文書であり、本仕様はその要求を実装可能な言語仕様へ変換した規範文書である。
要求と本仕様に差異がある場合は、要求文書の意図を優先し、仕様側を更新する。

### 1.6 用語

本仕様で用いる主要用語を定義する。

- 関数: 入力を受け取り値を返す評価単位。本仕様における実行の基本単位。
- タスク: 利用上の呼称であり、Lask では関数として表現される実行対象。
- モジュール: 宣言とインポートの集合であるソースファイル単位。
- 実行環境: コマンドを実行する対象コンテキスト。環境式 `#local` / `#docker(...)` / `#env(...)`（および Docker 糖衣 `#image-name`）で指定する。
- 環境定義ファイル: 名前付き環境（リモート接続先等）を定義する `environments.lask.json`（10.3）。
- 実行イベント: 呼び出し・戻り値・失敗を表す時系列記録単位。
- シリアル化: 値を外部表現に変換し保存・転送可能にする処理。
- コア式: 糖衣構文の静的展開（7.6）後に残る式。動的意味論（8 章）の評価対象。
- 糖衣構文: コア式へ正規化される表層構文。正規化後の式の意味論のみを規範とする（7.6）。
- コア関数: 糖衣構文の正規化先、または言語機能と一体の組み込み関数。ユーザーコードから宣言・上書きできない（7.2）。
- 組み込みライブラリ: 明示的なインポートなしで利用できる組み込みシンボル集合（15 章）。
- 実行前エラー: 関数評価の開始前（環境解決、引数束縛等）に検出・報告される失敗。

## 2. 記法

本章では、仕様文書全体で用いる EBNF 記法の読み方のみを定義する。

```ebnf
Production  = production_name "=" [ Expression ] "." .
Expression  = Alternative { "|" Alternative } .
Alternative = Term { Term } .
Term        = production_name | token [ "…" token ] | Group | Option | Repetition .
Group       = "(" Expression ")" .
Option      = "[" Expression "]" .
Repetition  = "{" Expression "}" .
```

EBNF の読み方:

- `A = B .` は「`A` を `B` として定義する」ことを表す。
- `|` は選択を表す。
- `{ X }` は `X` の 0 回以上の繰り返しを表す。
- `[ X ]` は `X` が省略可能であることを表す。
- `( X )` はグループ化を表す。
- `"..."` は終端記号（リテラル文字列）を表す。
- `production_name` は非終端記号（別の生成規則への参照）を表す。

## 3. 字句仕様

本章では、ソースコードを構成する字句要素を定義する。

共通字句要素:

- `unicode_char` は、改行を除く任意の Unicode スカラ値を表す終端記号とする。
- `newline` は改行（U+000A）とする。実装は CRLF（U+000D U+000A）を単一の改行として扱ってよい。

### 3.1 コメント

この仕様では、行コメントとブロックコメントの 2 種類を定義する。

```ebnf
line_comment  = "//" { unicode_char } .
block_comment = "/*" { unicode_char | newline | block_comment } "*/" .
```

規則:

- `unicode_char` は改行を含まないため、行コメントは改行の直前で終了する。
- ブロックコメントは `newline` を含められるため、複数行にまたがることができる。
- `block_comment` の定義に `block_comment` 自身を含めることで、ブロックコメントの入れ子を許可する。
- 入れ子許可により、大きな範囲を一時的にコメントアウトする際に、内部の既存 `/* ... */` を壊さず扱える。
- 実装はコメント深さを追跡し、最外層の `*/` でのみコメント終了と判定しなければならない。

### 3.2 識別子

```ebnf
identifier = lower_id | upper_id .
lower_id   = ( "a" … "z" | "_" ) { letter | decimal_digit | "_" } .
upper_id   = ( "A" … "Z" | "_" ) { letter | decimal_digit | "_" } .
letter        = "A" … "Z" | "a" … "z" .
decimal_digit = "0" … "9" .
```

規則:

- 識別子に `-` は含められない。`-` は常に二項演算子（6.2）として解釈されるため、`a-b` は一意に `a - b`（減算）と解析される。
- 複数語の識別子は `_`（`show_version`）を用いてスネークケースで構成する。
- CLI から関数を `-` 区切り名（`show-version`）で呼び出すための名前写像を 11.2 で定義する。識別子に `-` が含められないため、この写像は衝突しない。

### 3.3 リテラルと環境トークン

```ebnf
literal     = null_lit | bool_lit | number_lit | string_lit .
null_lit    = "null" .
bool_lit    = "true" | "false" .
number_lit  = decimal_digit { decimal_digit } [ "." decimal_digit { decimal_digit } ] .
string_lit  = raw_string_lit | interpreted_string_lit .
raw_string_lit         = "'" { raw_char | newline } "'" .
interpreted_string_lit = '"' { string_char | interpolation } '"' .
interpolation          = "#{" Expression "}" .
env_head    = "#" env_char { env_char } .
env_char    = letter | decimal_digit | "/" | ":" | "." | "-" | "_" | "@" .
```

`env_head` は `literal` には含まれない環境式（6.7）専用の字句トークンであり、本節では字句規則のみを定義する。

文字列リテラルのうち、`raw_string_lit` を生文字列、`interpreted_string_lit` を解釈文字列と呼ぶ。

文字列の文字クラスと終端規則:

- `raw_char` は `'` を除く `unicode_char` とする。生文字列は改行（`newline`）を含められるが、`'` そのものを含める手段は提供しない。`'` を含む文字列が必要な場合は解釈文字列を用いる。
- `string_char` は `"`・`\`・改行を除く `unicode_char`、またはエスケープシーケンスとする。解釈文字列に改行を直接含めることはできず、`\n` を用いる。
- 文字列リテラルは、最初に現れた対応する終端引用符で終端する。

字句規則:

- 空白（スペース、タブ）は、文字列リテラル・コマンド文字列（6.6）・コメント以外ではトークン区切りとして扱う。
- 連続する空白は 1 つの区切りと同等に扱う。
- 改行は独立したトークン（`newline`）として扱い、トップレベルでは宣言の終端（5 章の宣言終端規則）、`do` ブロック内部では文の終端（6.5 の文終端規則）、コマンド実行式ではコマンド文字列の終端（6.6）を表す。ただし 6.5 の継続規則に該当する改行は、トークン区切りの空白と同様に無視する。
- 連続する改行（空行）は、単一の改行トークンと同等に扱う。空行は宣言・文を生成しない。
- コメントは字句解析上は空白と同様に扱う。
- 行コメントは改行で終了し、ブロックコメントは `/*` と `*/` で囲まれる。
- 数値リテラルは符号を含まない。`-` と `+` は常に二項演算子として解釈する。負数はリテラルでは表現できず、`0 - 1` のような式で構成する（単項マイナスは提供しない）。
- `env_head` は環境式（6.7）の先頭トークンであり、最長一致で読む。`env_char` に該当しない文字（空白、`]`、`,`、`)`、`}` 等）が出現した位置で終端する。
- `env_char` を 1 文字も伴わない `#` は字句エラーとする（解釈文字列・コマンド文字列内の補間開始 `#{` を除く）。
- `env_char` の文字集合は、レジストリ・リポジトリ・タグ・ダイジェストを含む任意の Docker イメージ参照を表記できるよう定める。`@` はダイジェスト指定（例: `#alpine@sha256:...`）のために含む。

予約語:

- 次の語は予約語であり、識別子として使用してはならない。
- `import`, `from`, `as`, `type`, `do`, `async`, `await`, `if`, `else`, `for`, `return`, `try`, `catch`, `finally`, `true`, `false`, `null`
- `stdin` は予約語ではないが予約済み識別子であり（9.3）、ユーザーコードで宣言・再束縛してはならない。

文字列補間:

- 文字列補間は解釈文字列（`"..."`）でのみ使用できる。
- 補間開始は `#{`、終了は対応する `}` とする。
- 補間部は `Expression` として字句解析・構文解析される。
- 生文字列（`'...'`）では補間を行わず、内容をそのまま文字列値として扱う。

エスケープシーケンス:

- エスケープシーケンスは解釈文字列でのみ有効とする。
- 最低限サポートするエスケープは `\\`, `\"`, `\n`, `\r`, `\t` とする。
- Unicode エスケープは `\u{HEX}` 形式をサポートする（`HEX` は 1 文字以上の 16 進数）。
- 生文字列ではエスケープ処理を行わない。

## 4. 型システム

本章では、Lask が扱う値の型、型注釈、型推論、型互換性を定義する。

### 4.1 型の分類

- 基本型
  - `Any`: 任意の値を許容する汎用型
  - `Number`: 整数・浮動小数点数
  - `String`: UTF-8 文字列
  - `Bool`: 真偽値
  - `Null`: 値の不在
  - `Void`: 戻り値が存在しないこと
  - `Environment`: コマンドの実行環境（10 章）。値が環境式（6.7）でのみ構成され、シリアル化がメタデータ表現に限られる（4.5, 13.1）点で、他の基本型とは異なる特殊な位置付けを持つ。
- 合成型
  - `Array<T>`: 要素型 `T` を持つ配列
  - `Map<T>`: 文字列キーと値型 `T` を持つマップ
  - `Record<field1: T1, field2: T2, ...>`: 固定フィールドを持つレコード
  - `AsyncHandle<T>`: 非同期実行の結果 `T` を参照するハンドル
  - `Function<T1, T2, ..., R>`: 位置パラメータのみからなる関数型。最後の型引数を戻り値型とする。

### 4.2 型構文

```ebnf
Type              = BaseType | ArrayType | MapType | RecordType | AsyncHandleType | FunctionType | NamedType .
BaseType          = "Any" | "Number" | "String" | "Bool" | "Null" | "Void" | "Environment" .
ArrayType         = "Array" "<" Type ">" .
MapType           = "Map" "<" Type ">" .
RecordType        = "Record" "<" [ RecordFieldType { "," RecordFieldType } ] ">" .
RecordFieldType   = ( lower_id | string_lit ) ":" Type .
AsyncHandleType   = "AsyncHandle" "<" Type ">" .
FunctionType      = "Function" "<" Type { "," Type } ">" .
NamedType         = upper_id .
TypeAliasDecl     = "type" upper_id "=" Type .
```

Function 型の表現:

- `Function<T1, T2, ..., R>` は、位置順に `T1, T2, ...` を受け取り `R` を返す関数型を表す。
- `AsyncHandle<T>` は非同期実行中または完了済みの結果 `T` への参照を表す。
- `Function<R>` は引数を取らない関数を表す。

名前付き型の定義:

- 名前付き型は型エイリアス宣言 `type` で定義する。
- 形式は `type TypeName = Type` とする。
- 例: `type Strings = Array<String>`

レコードフィールド名:

- フィールド名は識別子形（`lower_id`）または文字列リテラル形（`string_lit`）で表記できる。同一性は文字列としての比較で判定し、`Record<name: String>` と `Record<"name": String>` は同一の型を表す。
- `lower_id` に適合しない名前（例: `"APP_ENV"`、`"X-Api-Key"`）は文字列リテラル形でのみ表記できる。
- 型表記およびオブジェクトリテラルのキーに用いる文字列リテラルは、補間（`#{...}`）を含んではならない。
- 同一レコード型・同一オブジェクトリテラル内でのフィールド名の重複（識別子形と文字列リテラル形の衝突を含む）は静的エラー（`E-TYPE-FIELD-DUPLICATE`）とする。
- `lower_id` に適合しないフィールド名へのアクセスは、文字列リテラル添字（6.8）を用いる。

型の整形規則（well-formedness）:

- `Void` は、関数型の戻り値位置（`Function<..., Void>`）および `AsyncHandle<Void>` の型引数としてのみ出現できる。`Array`・`Map` の型引数、レコードのフィールド型、関数型のパラメータ位置への出現は静的エラー（`E-TYPE-ILLFORMED`）とする。
- 組み込み多相（4.4）の型変数の具体化を含め、型検査中に構成されるすべての型は本整形規則を満たさなければならない（例: `map` の結果型を `Array<Void>` とする具体化は `E-TYPE-ILLFORMED`。`spawn` による `AsyncHandle<Void>` の構成は合法である）。
- 型エイリアス（`TypeAliasDecl`）は、直接にも間接にも自身を参照してはならない（再帰・相互再帰の禁止）。違反は静的エラー（`E-TYPE-ILLFORMED`）とする。この規則により `NamedType` の展開（4.3）は有限回で必ず停止する。

例:

- 基本型
  - `Number`
  - `String`
  - `Environment`
- 配列型
  - `Array<Number>`
  - `Array<Record<name: String, age: Number>>`
- マップ型
  - `Map<String>`
  - `Map<Array<Number>>`
- レコード型
  - `Record<name: String, age: Number>`
  - `Record<env: Environment, tags: Array<String>>`
  - `Record<"APP_ENV": String, "REGION": String>`
- 関数型
  - `Function<Number, Number, Number>`
  - `Function<String, Record<message: String, ok: Bool>>`
  - `Function<Number>`
- 名前付き型
  - `Strings` （`type Strings = Array<String>`）
  - `User`
  - `BuildConfig`

### 4.3 型注釈と推論

型注釈は任意とし、注釈がない箇所には以下の規則で型推論を適用する。

- 注釈が与えられている場合は、その注釈を優先し、推論結果の型は注釈型に適合（4.4 の適合関係）しなければならない。
- 型注釈（変数・パラメータ・戻り値）および呼び出し先の引数型は、対応する式に対する期待型として伝播し、リテラルの期待型指向の検査（後述）に用いる。
- 数値リテラルは `Number`、文字列リテラルは `String`、真偽値リテラルは `Bool`、`null` リテラルは `Null` とする。環境式 `#...`（6.7）は `Environment` とする。
- 配列リテラル `[e1, e2, ...]` は、期待型がない場合、各要素型を推論し、すべて同一型 `T` なら `Array<T>`、異種混在なら `Array<Any>` とする。
- 期待型が `Array<T>` の場合、すべての要素式が `T` に適合すればリテラルの型を `Array<T>` とする。適合しない要素があれば型エラーとする（適合は不変（4.4）だが、リテラルは期待型指向の検査により要素単位で `Any` 等へ昇格できる）。
- 空配列 `[]` は期待型があればそれに従い、期待型がない場合は `Array<Any>` とする。
- オブジェクトリテラル `{k1: e1, ...}` は、期待型がない場合 `Record<k1: T1, ...>` として推論する（`Ti` は各 `ei` の推論型）。キーが文字列リテラルの場合は、その文字列をフィールド名とする（4.2 のレコードフィールド名規則）。
- 期待型があるオブジェクトリテラルは、次の規則で期待型と矛盾しないかを検査する。
  - 期待型が `Record<...>` の場合: リテラルのキー集合は期待型のフィールド集合と一致し（キーの同一性は 4.2 のフィールド名規則に従う）、各値式は対応するフィールド型に適合しなければならない。キーの過不足・型不適合は型エラーとする。
  - 期待型が `Map<T>` の場合: すべての値式が `T` に適合するとき、リテラルの型を `Map<T>` とする。適合しない値がある場合は型エラーとする（キーは常に `String` として扱う。4.4）。
  - 期待型が `Any` の場合: 期待型がない場合と同様に `Record<...>` として推論する。
  - それ以外の期待型の場合は型エラーとする。
- 変数・関数宣言で注釈がない場合、右辺式の型を宣言型として採用する。
- 関数の戻り値注釈がない場合、関数本体の型を戻り値型として推論する。
- パラメータ注釈がない場合、`Any` を採用する。
- 関数呼び出し `f(a1, ..., an)` では、`f` が `Function<T1, T2, ..., Tm, R>` に解決され、引数束縛が 7.5 の規則（キーワード引数・既定値補完を含む）を満たし、束縛された各引数が対応する位置の型に適合しなければならない。結果型は `R` とする。
- `Function<T1, T2, ..., R>` の形式では、最後の型引数を戻り値型とし、それ以前を位置パラメータ型とする。
- `NamedType` は型検査前に `TypeAliasDecl` へ展開し、推論は展開後の型で行う。
- オーバーロードはサポートしない。1 つのシンボルは 1 つの関数型を持つ。
- 抽象型（型クラス等）はサポートしない。ユーザーコードでの型変数の宣言・多相型注釈もサポートしない。組み込みシンボルに限り、4.4 の組み込み多相規則に従う。

推論失敗時の診断規則:

- 式の型が注釈型に適合しない場合は型エラーとする。
- 呼び出し時に引数束縛が 7.5 の規則を満たさない場合、または引数型が適合しない場合は型エラーとする。
- 複数の制約が競合し、単一の型に統合できない場合は型エラーとする。
- 単一の最終型に確定できない場合は推論失敗エラーとする。

型推論の例:

- `n = 1` は `n: Number` と推論される。
- `ok = true` は `ok: Bool` と推論される。
- `names = ["a", "b"]` は `names: Array<String>` と推論される。
- `mixed = [1, "a"]` は `mixed: Array<Any>` と推論される。
- `empty = []` は期待型がなければ `empty: Array<Any>` と推論される。
- `user = {name: "alice", age: 20}` は `user: Record<name: String, age: Number>` と推論される。
- `envMap: Map<String> = {"APP_ENV": "prod", "REGION": "ap-northeast-1"}` は、期待型 `Map<String>` により `Map<String>` として型付けされる。
- `hdrs = {"X-Api-Key": "secret"}` は、期待型がないため `hdrs: Record<"X-Api-Key": String>` と推論される。
- `bad: Map<Number> = {"a": "x"}` は、値 `"x"` が `Number` に適合しないため型エラーとなる。
- `add(x: Number, y: Number) = x + y` の呼び出し `add(1, 2)` は結果型 `Number` と推論される。
- `identity(x) = x` は、パラメータ注釈とデフォルト値がないため `identity: Function<Any, Any>` と推論される。
- `inc(--x = 0) = x + 1` は、既定値 `0` からキーワードパラメータ `x: Number` が推論され、`inc: Function<Number>`（位置パラメータなし）と推論される。呼び出し `inc()` と `inc(x = 5)` はいずれも合法であり、結果型は `Number` となる。
- `type Strings = Array<String>` があるとき、`xs: Strings = ["a"]` は `xs: Array<String>` と同値として扱われる。

### 4.4 型の意味論

型の適合関係:

型検査における「適合」は、次で定義される二項関係である。式の型 `T` が要求位置の型 `U` に適合するとき、その式は `U` を要求する位置（引数、注釈付き宣言の右辺、フィールド値、戻り値等）に置ける。

- 反射律: `T` は `T` に適合する。型の同一性は、`NamedType` を展開（4.3）した後の構造的同一で判定する。
- 上位型: 任意の `T` は `Any` に適合する。`Any` は唯一の上位型である。
- 上記以外の型の組に適合関係はない。

不変性（変性を導入しない）:

- 適合は型構成子の内部へ持ち上げない（不変）。`Array<Number>` は `Array<Any>` に適合しない（要素型は同一でなければならない）。`Map`・`AsyncHandle` も同様とする。
- `Record` は幅・深さの部分型を持たない。フィールド集合と各フィールド型が同一の場合にのみ適合する。
- 関数型は同一の場合にのみ適合する。引数位置・戻り値位置への変性（反変・共変）は導入しない。
- この定義により、部分型付けに伴う変性の健全性条件（関数引数位置の反変性等）は発生しない。

型の意味は次の規則で定義する。

- `Any` はすべての型の値を受け入れる唯一の上位型とする（任意の型が `Any` に適合する）。
- `Any` 型の式は、`Any` を要求する位置にのみ置ける。`Any` から具体型への移行は、実行時型検査を伴う `cast`（15.8）によってのみ行える。静的な暗黙変換は提供しない。
- `Null` は値の不在を表す値型であり、式として評価可能である。
- `Void` は値を返さない計算結果を表す型であり、値として利用してはならない。
- `Null` と `Void` は同一視しない。`Null` を要求する位置に `Void` を置くこと、およびその逆は型不一致とする。
- `Array<T>` は要素が一様に `T` である配列を表す。
- 要素型が混在する配列は `Array<Any>` として扱う。
- `Map<T>` は文字列キーを持つ動的連想配列を表す組み込み合成型であり、キー型は常に `String` に固定される。
- `Record<...>` はフィールド集合と各フィールド型が静的に確定した構造を表す。
- `Map<T>` はキー集合が実行時に変動し得る構造、`Record<...>` は仕様上固定されたキー集合を持つ構造として役割分担する。
- `AsyncHandle<T>` は非同期計算のライフサイクルを管理する実行時ハンドルであり、`await` により `T` へ解決される。
- 関数型 `Function<T1, T2, ..., R>` 同士の適合は、本節冒頭の適合関係に従い、位置パラメータの個数・各パラメータ型・戻り値型がすべて同一の場合に限る（`Any` への昇格はトップレベルの `Any` を要求する位置でのみ生じる）。
- パラメータ名・キーワードパラメータ・可変長性は関数型の一部ではない。関数値として受け渡した後の適用では宣言パラメータ情報を参照できないため、束縛は位置引数のみで行い、キーワードパラメータはすべて既定値で補完される（7.5）。
- オーバーロードを許可しないため、1 つの関数シンボルに複数の関数型を同時に割り当ててはならない。
- `NamedType` は対応する `TypeAliasDecl` に展開した後の型と同値に扱う。

組み込みシンボルの多相型（組み込み多相）:

- 本仕様の型構文（4.2）に型変数は存在せず、ユーザーコードは多相型を宣言できない。ユーザーコードの型注釈に現れる `upper_id` は常に `NamedType`（型エイリアス参照）として解決され、対応する宣言がなければ未定義参照エラーとする。
- ただし、仕様が定義する組み込みシンボル（コア関数および組み込みライブラリの関数。6 章、15 章）に限り、署名に型変数（`T`、`U`、`R` 等の単一大文字名）を含む多相型を持つことができる。
- 型変数を含む署名は型スキームとして扱い、呼び出しごとに独立して具体型へ具体化（インスタンス化）して検査する。同一呼び出し内では、同名の型変数は同一の具体型に束縛されなければならない。
- 具体化は引数の型と文脈の期待型から決定する。単一の具体型へ決定できない場合は推論失敗エラー（4.3）とする。
- 組み込み多相関数を呼び出し以外の位置で関数値として参照する場合（変数への束縛、引数への受け渡し等）は、参照位置の期待型から型変数を一意に具体化できなければならない。具体化できない場合は型エラーとする。例: `m: Function<Array<Number>, Function<Number, Number>, Array<Number>> = map` は期待型注釈により具体化できるが、注釈のない `m = map` は推論失敗エラーとなる。
- 実装は組み込み多相を任意の内部機構で実現してよいが、上記の観測可能な型検査結果を満たさなければならない。多相をユーザー定義シンボルへ拡張してはならない。

### 4.5 シリアライズ対象と非対象

- 直接シリアライズ対象
  - `Any`, `Number`, `String`, `Bool`, `Null`
  - `Array<T>`, `Map<T>`, `Record<field1: T1, field2: T2, ...>`
- 直接シリアライズ非対象
  - `Void`, `Environment`
  - `AsyncHandle<T>`
  - `Function<T1, T2, ..., R>`
- 関数値は実行記録・外部出力では参照メタデータ（`FunctionRef`。13.2）へ変換する。
- `Void`・`Environment` も同様に、外部出力ではタグ付きメタデータ表現（13.1）へ変換する。いずれもデシリアライズによる復元は保証されない（13.1 の往復規則）。

## 5. 宣言とモジュール

本章では、モジュール、宣言、公開シンボル、インポートを定義する。

```ebnf
Module        = { TopLevelDecl } .
TopLevelDecl  = ( ImportDecl | TypeAliasDecl | Declaration ) decl_end .
decl_end      = newline | ";" .
TypeAliasDecl = "type" upper_id "=" Type .
Declaration = ValueDecl | FunctionDecl .
ValueDecl   = lower_id [ ":" Type ] "=" Expression .
FunctionDecl = lower_id "(" [ FunctionParameterList ] ")" [ ":" Type ] "=" Expression .

ImportDecl      = "import" ( NamedImports | NamespaceImport ) "from" ImportPath .
NamedImports    = "{" ImportSpecifier { "," ImportSpecifier } "}" .
ImportSpecifier = ( lower_id | upper_id ) [ "as" ( lower_id | upper_id ) ] .
NamespaceImport = "*" "as" lower_id .
ImportPath      = string_lit .
```

宣言終端規則:

- トップレベル宣言は、改行、`;`、またはファイル終端で終端する。ファイル終端の直前では `decl_end` を省略できる。
- 終端・継続の判定は 6.5 の文終端規則（継続トークン、行頭トークンによる継続、行頭の `(`・`[` の扱い）と同一とする。継続規則により宣言の右辺は複数行にまたがることができる。
- `;` は 1 行に複数の宣言を記述するための任意の区切りであり、行末では記述を要しない。
- `as`・`from` は継続トークンではない（6.5）。`import` 宣言は、`NamedImports` の波括弧内部（開き括弧の継続規則により複数行可）を除き 1 行で記述する。閉じ `}` と `from` 句は同一行に置かなければならない。
- 行頭の `(`・`[` は直前の宣言の継続とはならず、新しい宣言の開始として解釈する。トップレベル宣言は `import`・`type`・識別子のいずれかで始まるため、この場合は構文エラーとなる。

モジュールの読み込み単位:

- 1 つのソースファイルを 1 つのモジュールとみなす。
- モジュールは `import` 宣言で他モジュールへ依存できる。
- `ImportPath` は実装が解決可能なモジュール識別子として扱う。

公開範囲と可視性:

- トップレベルで宣言された `Declaration` と `TypeAliasDecl` は、そのモジュールの公開シンボルとする。
- モジュール内部で定義されたローカル束縛（関数引数、`do` 内の束縛等）は公開しない。
- 同一モジュール内で同名のトップレベルシンボルを複数回宣言してはならない。

インポート形式:

- 名前付きインポート `import { a, b } from "path"` は、対象モジュールの公開シンボルのうち指定した名前だけを現在モジュールの名前解決対象へ取り込む。指定した名前が公開シンボルに存在しない場合は型検査前エラーとする。
- `import { a as b } from "path"` は、公開シンボル `a` を名前 `b` として取り込む（改名インポート）。改名前後の識別子は同じ種別（`lower_id` 同士、`upper_id` 同士）でなければならない。
- 名前空間インポート `import * as m from "path"` は、対象モジュールを名前空間 `m` で参照する。公開シンボルは暗黙には取り込まれず、`m.symbol` 形式で参照する。
- 型エイリアス（`upper_id`）は名前付きインポートで取り込める。型注釈での参照は `NamedType`（4.2）が単一の `upper_id` に限られるため、名前空間経由の型参照（`m.TypeName`）はできない。型を利用する場合は名前付きインポートを用いる。
- すべての公開シンボルを無条件に取り込む形式は提供しない（取り込む名前を宣言で明示するため）。

同名シンボル衝突時の規則:

- 現在モジュールのトップレベル宣言と、名前付きインポートで取り込まれたシンボル（改名後の名前）が同名の場合は型検査前エラーとする。
- 名前付きインポート同士で、取り込み後の名前が衝突する場合は型検査前エラーとする。
- 名前空間インポートの名前空間名が重複する場合、およびトップレベル宣言・取り込み済みシンボルと同名の場合は型検査前エラーとする。

循環インポートの扱い:

- モジュール依存グラフは有向非循環グラフ（DAG）でなければならない。
- 循環インポートを検出した場合、実行前にモジュール解決エラーとする。

記述例:

```lask
// module: lib/math.lask
add(x: Number, y: Number): Number = x + y
```

```lask
// module: lib/types.lask
type Strings = Array<String>
joinWithComma(xs: Strings): String = join(xs, ",")
```

```lask
// module: app/main.lask
import { add } from "lib/math.lask"
import * as types from "lib/types.lask"

sum2(a: Number, b: Number) = add(a, b)
labels = ["a", "b", "c"]
csv = types.joinWithComma(labels)
```

## 6. 式

本章では、Lask の式を定義する。Lask のすべての実行単位は式として表現される。

```ebnf
Expression   = UnaryExpr | Expression binary_op Expression .
UnaryExpr    = PrimaryExpr | unary_op UnaryExpr .
PrimaryExpr  = operand | AccessorExpr | CallExpr | DoExpr | IfExpr | ForExpr | TryExpr | AsyncExpr | AwaitExpr .

operand      = literal | lower_id | array_lit | object_lit | "(" Expression ")" | LambdaExpr | CommandExpr | EnvExpr .
array_lit    = "[" [ Expression { "," Expression } ] "]" .
object_lit   = "{" [ KeyValuePair { "," KeyValuePair } ] "}" .
KeyValuePair = ( lower_id | string_lit ) ":" Expression .

AccessorExpr = PrimaryExpr "." lower_id | PrimaryExpr "[" Expression "]" .
CallExpr     = PrimaryExpr "(" [ Arguments ] ")" .
Arguments    = Argument { "," Argument } .
Argument     = [ lower_id "=" ] Expression .
```

### 6.1 関数パラメータ・ラムダ式・高階関数

```ebnf
FunctionParameterList = PositionalParameters [ "," VariadicParameter ] [ "," KeywordParameters ]
                      | VariadicParameter [ "," KeywordParameters ]
                      | KeywordParameters .
PositionalParameters  = PositionalParameter { "," PositionalParameter } .
PositionalParameter   = lower_id [ ":" Type ] .
VariadicParameter     = "..." lower_id [ ":" ArrayType ] .
KeywordParameters     = KeywordParameter { "," KeywordParameter } .
KeywordParameter      = "--" lower_id [ ":" Type ] "=" Expression .
LambdaExpr            = "\\" "(" [ FunctionParameterList ] ")" [ ":" Type ] "->" Expression .
```

パラメータ記法の意味:

- パラメータは宣言時に、位置パラメータ（`name`）、可変長パラメータ（`...name`）、キーワードパラメータ（`--name`）のいずれかとして明確に区別する。宣言順は、位置パラメータ列、可変長パラメータ（高々 1 つ）、キーワードパラメータ列の順とする（文法による）。
- 位置パラメータは位置引数でのみ束縛される。すべて必須であり、既定値を持てない。
- キーワードパラメータは名前でのみ束縛される（言語内の呼び出しでは `name = 式`、CLI では `--name <value>`。11.2）。既定値式を必ず持ち、未指定時は既定値で補完される。
- 位置パラメータを名前で束縛すること、およびキーワードパラメータを位置で束縛することはできない（`E-TYPE-KEYWORD`）。
- `--` はキーワードパラメータの宣言標識としてのみ現れる字句であり、演算子 `-` の連続としては解釈しない。
- パラメータ名は、関数本体内での参照と、キーワードパラメータの束縛インターフェースに用いる（本体内の参照はどの種別も `name` で行う）。

キーワード引数:

- 呼び出しの引数は `名前 = 式`（`Argument = [ lower_id "=" ] Expression`。6 章冒頭）の形でキーワードパラメータを指定して与えられる。
- 位置引数は、すべてのキーワード引数より前に置かなければならない。
- キーワード引数の名前は、呼び出し先のキーワードパラメータ名（7.5 の宣言パラメータ情報）と一致しなければならない。未知の名前、位置パラメータ・可変長パラメータの名前指定、および同一パラメータへの重複束縛は静的エラー（`E-TYPE-KEYWORD`）とする。
- キーワード引数は、呼び出し先が関数宣言・ラムダ式へ静的に解決される場合にのみ使用できる。関数型の値としてのみ解決される呼び出し（7.5）では宣言パラメータ情報を参照できないため位置引数のみを受け付け、キーワードパラメータはすべて既定値で補完される。
- キーワード引数の記述順は任意である（例: `f(1, c = 3, b = 2)`）。

可変長パラメータ:

- 位置パラメータ列の直後に、高々 1 つの可変長パラメータ `...name` を宣言できる（キーワードパラメータはその後ろに置く）。
- 可変長パラメータの型注釈は `Array<T>` の形でなければならない。注釈がない場合は `Array<Any>` とする。関数本体内では `Array<T>` 型の値として参照する。
- 可変長パラメータは既定値式を持てない。対応する位置引数が 0 個の場合、空配列 `[]` が束縛される。
- 位置パラメータをすべて束縛した後の残りの位置引数が、記述順に収集されて 1 つの配列として束縛される。各引数は要素型 `T` に適合しなければならない。
- 可変長パラメータはキーワード引数で束縛できない（`E-TYPE-KEYWORD`）。
- 関数型上、可変長パラメータは対応する配列型の 1 パラメータとして現れる（例: `sum(...xs: Array<Number>): Number` は `Function<Array<Number>, Number>`）。可変長性は関数型には含まれず、宣言パラメータ情報（7.5）として保持する。したがって関数値経由の適用（7.5）では、配列を 1 つの位置引数として明示的に渡す。

記述例:

```lask
sum(...xs: Array<Number>): Number =
  reduce(xs, 0, \(acc: Number, x: Number) -> acc + x)

s1 = sum()
s2 = sum(1, 2, 3)

f: Function<Array<Number>, Number> = sum
s3 = f([1, 2, 3])
```

記述例:

```lask
greet(name: String, --prefix: String = "hello"): String =
  concat(prefix, concat(", ", name))

g1 = greet("alice")
g2 = greet("alice", prefix = "hi")
```

関数宣言の糖衣規則:

- `name(p1, p2, ..., pn) = body` は `name = \(p1, p2, ..., pn) -> body` と同値である。
- `FunctionDecl` のパラメータ仕様は `LambdaExpr` の `FunctionParameterList` と同一規則に従う。
- したがって、宣言にパラメータを含める記法は、ラムダ式を値として代入する記法の糖衣である。

同値例:

```lask
f(x) = x + 1
g = \(x) -> x + 1
```

上記の `f` と `g` は本質的に同じ関数を宣言している。

### 6.2 演算子

```ebnf
unary_op  = "!" .
binary_op = "*" | "/" | "+" | "-" | "==" | "!=" | "<" | "<=" | ">" | ">="
          | "&&" | "||" | "|>" | "<|" | ">>" | "<<" .
```

演算子は、関数適用を読みやすく記述するための構文糖衣である。演算子自体はユーザー定義できず、評価系が固定の意味を持つ。

演算子の優先順位は高い順に次の通りとする。

1. 単項演算子 `!`
2. 乗除演算子 `*` `/`
3. 加減演算子 `+` `-`
4. 比較演算子 `==` `!=` `<` `<=` `>` `>=`
5. 論理演算子 `&&` `||`
6. パイプ・合成演算子 `|>` `<|` `>>` `<<`

同じ優先順位を持つ演算子は、左から右へ結合する。

各演算子の意味は次の通りとする。

- `!e` は真偽値の否定を表す。
- `e1 * e2`, `e1 / e2`, `e1 + e2`, `e1 - e2` は算術演算を表す。
- `e1 == e2`, `e1 != e2` は値の比較を表す。
- `e1 < e2`, `e1 <= e2`, `e1 > e2`, `e1 >= e2` は順序比較を表す。
- `e1 && e2` は左辺が偽のとき右辺を評価せず、左辺が真のときのみ右辺を評価する。
- `e1 || e2` は左辺が真のとき右辺を評価せず、左辺が偽のときのみ右辺を評価する。
- `e1 |> f` は `f(e1)` の糖衣である。
- `f <| e1` は `f(e1)` の糖衣である。
- `f >> g` は `\(x) -> g(f(x))` に相当する関数合成を表す。
- `f << g` は `\(x) -> f(g(x))` に相当する関数合成を表す。

演算子の型は次の通りとする。

- `!` は `Function<Bool, Bool>` として型付けする。
- `*`, `/`, `+`, `-` は `Function<Number, Number, Number>` として型付けする。
- `<`, `<=`, `>`, `>=` は `Function<Number, Number, Bool>` として型付けする。
- `&&`, `||` は `Function<Bool, Bool, Bool>` として型付けする。
- `==`, `!=` は左右の型が一致し、かつその型が比較可能型である場合にのみ型付け可能とし、結果型は `Bool` とする。
- 比較可能型は、`Number`、`String`、`Bool`、`Null`、`Environment`、および要素・値・フィールドの型がすべて比較可能型である `Array<T>` / `Map<T>` / `Record<...>` に限る。
- `Function`・`AsyncHandle`・`Void`・`Any` を含む型への `==` / `!=` の適用は静的エラーとする。`Any` の値を比較する場合は、`cast`（15.8）で具体型へ移行してから比較する。
- 構造値（`Array` / `Map` / `Record`）の等価性は、要素・キー・フィールドの再帰的な構造比較で判定する。`Environment` の等価性は 8.8 に従う。
- `e1 |> f` は、`e1: T` かつ `f: Function<T, R>` を満たすとき型付け可能で、式全体の型は `R` とする。
- `f <| e1` は、`e1: T` かつ `f: Function<T, R>` を満たすとき型付け可能で、式全体の型は `R` とする。
- `f >> g` は、`f: Function<T, U>` かつ `g: Function<U, R>` を満たすとき型付け可能で、式全体の型は `Function<T, R>` とする。
- `f << g` は、`g: Function<T, U>` かつ `f: Function<U, R>` を満たすとき型付け可能で、式全体の型は `Function<T, R>` とする。

パイプ・合成演算子は、関数の受け渡しを左から右へ読みやすくするための糖衣であり、括弧を用いて結合順を明示できる。

比較演算子や論理演算子の結果は `Bool` とする。算術演算子の結果は `Number` とし、数値演算として評価可能でなければならない。
`+` を含む算術演算子は `Number` 専用であり、`String` へ適用した場合は型エラーとする。文字列の連結は演算子では行わず、組み込みライブラリの `concat`（15.3）を用いる。

### 6.3 非同期呼び出しと待機

```ebnf
AsyncExpr = "async" UnaryExpr .
AwaitExpr = "await" UnaryExpr .
```

本節では、非同期起動の糖衣構文 `async` と、待機を表す組み込みコア関数 `await` を定義する。

関数としての定義:

- `spawn` は引数として受け取った無引数関数を非同期で起動し、結果ハンドルを返すコア関数である。
- `await` は結果ハンドルを受け取り、完了値へ合流するコア関数である。

構文規則:

- `async e` は `spawn(\() -> e)` の糖衣である。`async` は被演算子 `e` の評価を遅延させる必要があるため、関数ではなく糖衣構文として提供する。
- `await e` は、コア関数 `await` を被演算子 `e` へ適用する括弧省略形である。`await (e)` と記述した場合も、括弧付きの被演算子を持つ `AwaitExpr` として同一規則で解析され、意味は同じである。
- `AsyncExpr` / `AwaitExpr` の被演算子は `UnaryExpr` とする。したがって `await h |> f` は `(await h) |> f` と解釈される。`await (h |> f)` の意味にしたい場合は括弧で明示する。
- `await` は予約語であり、`AwaitExpr` の形でのみ出現できる。関数値として受け渡す場合は `\(h) -> await h` と記述する。

ここで `spawn` と `await` はコア関数であり、ユーザーコードから直接宣言・上書きしてはならない。

型規則:

- `e: T` のとき、`async e` の型は `AsyncHandle<T>` とする。
- `f: Function<T>` のとき、`spawn(f)` の型は `AsyncHandle<T>` とする。
- `h: AsyncHandle<T>` のとき、`await h` の型は `T` とする。
- `await` に `AsyncHandle<...>` 以外を渡した場合は型エラーとする。

評価規則:

- `async e` は呼び出し時点で評価を開始し、呼び出し元には直ちにハンドル値 `AsyncHandle<T>` を返す。
- `await h` は `h` が完了するまで現在の評価を停止し、完了後に結果値を返す。
- `await h` を同一ハンドルへ複数回適用した場合、同一の完了結果を返す。
- `async e` 内で失敗が発生した場合、`await h` 時にその失敗を再送出する。

実行環境は `async` の並行実行方式（スレッド、イベントループ、リモート実行キュー等）を実装定義として選択できるが、上記の型規則と評価規則を満たさなければならない。

### 6.4 制御構造

```ebnf
IfExpr  = "if" "(" Expression ")" Block "else" Block .
ForExpr = "for" "(" lower_id ":" Expression ")" Block .
Block   = "{" { DoStmt } "}" .
```

制御構造はブロック形式の式 `IfExpr` / `ForExpr` として提供し、意味論上はコア関数 `choose` とコレクション関数 `map` へ正規化して扱う。`if` / `for` は予約語であり、本節の式形でのみ出現できる（関数呼び出し形 `if(c, t, f)` / `for(xs, body)` は提供しない）。

`IfExpr` / `ForExpr` は `PrimaryExpr`（6 章冒頭）であり、束縛の右辺・関数本体・引数など、式を置ける任意の位置に出現できる。

関数としての定義:

- `choose` は条件値と 2 つの分岐関数を受け取り、いずれか一方だけを評価するコア関数である。
- コレクションに対する反復は、用途別のコア関数 `map` / `filter` / `reduce` / `forEach`（15.4）で表現する。
  - `map` は各要素へ本体関数を適用し、結果を同順序の配列として返す。
  - `filter` は述語が真を返した要素だけを同順序で残す。
  - `reduce` は初期値と畳み込み関数でコレクションを単一値へ集約する。
  - `forEach` は各要素へ本体関数を適用し、結果を捨てて `Void` を返す（副作用目的の反復）。

糖衣規則:

- `if (c) { ... } else { ... }` は `choose(c, \() -> do { ... }, \() -> do { ... })` の糖衣である。
- `for (x : xs) { ... }` は `map(xs, \(x) -> do { ... })` の糖衣である。ただし本体ブロックの型が `Void` の場合（空ブロックを含む）は `forEach(xs, \(x) -> do { ... })` の糖衣とする（`Array<Void>` は構成しない。4.4）。
- 結果配列が不要な副作用目的の反復には、本体を `Void` 型にするか、`forEach` を直接用いる。

ここで `choose` は正規化先を表すためだけのコア関数であり、組み込みライブラリには公開されない（ユーザーコードから参照・宣言・上書きできない）。`map` / `filter` / `reduce` / `forEach` は組み込みライブラリの関数（15.4）であると同時に正規化先のコア関数であり、同様に上書きしてはならない。

型規則:

- `choose` は `Function<Bool, Function<T>, Function<T>, T>` として型付けする。
- `map` は `Function<Array<T>, Function<T, U>, Array<U>>` として型付けする。
- `filter` は `Function<Array<T>, Function<T, Bool>, Array<T>>` として型付けする。
- `reduce` は `Function<Array<T>, U, Function<U, T, U>, U>` として型付けする。
- `forEach` は `Function<Array<T>, Function<T, U>, Void>` として型付けする（本体の戻り値型 `U` は任意であり、結果は捨てられる。`Any` ではなく型変数 `U` を用いるのは、関数型の適合が同一性に限られる（4.4）ため、任意の戻り値型の本体を組み込み多相の具体化で受けるためである）。
- `IfExpr` は、条件式が `Bool` であり、2 つの分岐ブロックの型が同一の `T` である場合にのみ型付け可能とし、式全体の型は `T` とする。
- `else` を持たない `if` は式ではない。唯一、`return` ガード文（6.5 の `GuardStmt`）として文位置にのみ現れる。
- `ForExpr` は、対象式が `Array<T>`、本体ブロックの型が `R`（`R` は `Void` 以外）のとき、式全体の型を `Array<R>` とする。
- 本体ブロックの型が `Void` の場合、`ForExpr` は `forEach` へ正規化され、式全体の型は `Void` とする。

評価規則:

- `IfExpr` は条件式のみを先に評価し、真なら then ブロック、偽なら else ブロックだけを評価する（8.5 の `choose` に従う）。
- `ForExpr` は対象コレクションを評価した後、要素を左から右へ走査して本体ブロックを適用し、結果を同順序の配列へ集約する（8.5 の `map` に従う）。
- `Block` の内部は `do` ブロックと同一の文規則（6.5）に従い、ブロックの値は末尾文の値とする。文を持たない空ブロックの値は `Void` とする（6.5）。

### 6.5 手続的記述

```ebnf
DoExpr     = "do" Block .
DoStmt     = ( BindStmt | ExprStmt | ReturnStmt | GuardStmt ) stmt_end .
BindStmt   = lower_id "=" Expression .
ExprStmt   = Expression .
ReturnStmt = "return" Expression .
GuardStmt  = "if" "(" Expression ")" Block .
stmt_end   = newline | ";" .
```

ここで `Block` は 6.4 で定義するブロック（`"{" { DoStmt } "}"`）、`newline` は 3.3 で定義する改行トークンとする。ブロック終端 `}` の直前では `stmt_end` を省略できる。
`if` / `for` のブロック形式は式（6.4 の `IfExpr` / `ForExpr`）であるため、専用の文形式は存在しない。`ExprStmt` として、または `BindStmt` の右辺として出現する。

文終端規則:

- `do` ブロック内の文は、改行、`;`、またはブロック終端 `}` の直前で終端する。
- `;` は 1 行に複数の文を記述するための任意の区切りであり、行末では記述を要しない（記述しても誤りではない）。
- 次のいずれかに該当する改行は文終端とみなさず、文の継続として扱う。
  - 文の内部で開いた括弧（`(`、`[`、`{`）がまだ閉じていない位置の改行
  - 行末のトークンが継続トークンである位置の改行。継続トークンは次に限定する: `=`、`,`、`:`、`->`、二項演算子（`|>`、`+`、`==` 等。6.2 の `binary_op`）、`!`
  - 次の行の先頭トークンが二項演算子（`|>`、`+`、`==` 等）である場合の改行
  - 次の行の先頭トークンが `else` である場合の改行（`IfExpr` の then ブロック閉じ `}` の後の継続）
  - 次の行の先頭トークンが `catch` または `finally` である場合の改行（`TryExpr` のブロック閉じ `}` の後の継続）
- `as` および `from` は継続トークンでも継続の先頭トークンでもない。行頭の `as`・`from` は直前の文・宣言の継続とはならない（5 章の `import` 宣言の制約を参照）。
- 行頭の `(` および `[` は新しい文の開始として解釈する。直前の文の呼び出し引数リストや添字アクセスを、行頭の `(`・`[` から始めてはならない。
- 数値リテラルは符号を含まない（3.3）ため、行頭の `-`・`+` は常に直前の文の継続（二項演算子）として一意に解釈される。
- 本節以降の規則・例に現れる文区切りの `;` は改行と読み替えてよい。両者は文終端として同義である。
- 本規則（終端・継続の判定）は、トップレベル宣言の終端（5 章の宣言終端規則）にも同一に適用される。

手続的記述は、式中心のコア言語へ段階的に移行しやすくするための糖衣構文である。
`do` は逐次評価の糖衣であり、`if (...) { ... } else { ... }` / `for (...) { ... }` は 6.4 の規則で `choose` / `map` を使う式へ正規化される。

目的と設計方針:

- 手続的な見た目を許容しつつ、意味論は関数適用と式評価に統一する。
- `do` は逐次評価順のみを与え、独自の実行モデルは導入しない。
- 制御は必ず関数（`choose` / `map` 等のコレクション関数）へ落とし、評価規則の重複を避ける。

糖衣規則:

- `if (...) { ... } else { ... }` / `for (...) { ... }` の糖衣規則は 6.4 に従う。
- `do { e }` は `e` と同値である。
- `do { v = e1; s2; ...; sn; }` は、`e1` を先に評価して `v` に束縛し、その後 `s2 ... sn` を評価する式へ正規化される。
- `do { e1; s2; ...; sn; }` は、`e1` の値を捨てて `s2 ... sn` を評価する式へ正規化される。

逐次実行の糖衣:

- `do { stmt1; stmt2; ...; expr; }` は、各文を順に評価して最後の式の値を返す逐次実行の糖衣である。
- `do` 内の束縛は順序に従って可視化され、後続の文から参照できる。

早期終了（`return`）:

- `return e` は、それを含む最も内側の関数（関数宣言またはラムダ式）の本体の残りの評価を行わず、`e` をその関数の結果とする文である。
- `return` を置けるのは次の位置に限る（return 可能位置）。違反は構文エラー（`E-SYNTAX-RETURN-POSITION`）とする。
  - 関数宣言・ラムダ式の本体である `do` ブロックの文位置
  - return 可能位置に置かれた `GuardStmt`、および文位置の `IfExpr` の各分岐ブロック内の文位置（再帰的に適用する）
- したがって、`for` の本体、`try`/`catch`/`finally` の各ブロック、および束縛の右辺・引数など式位置に現れる `do` ブロックの内部では使用できない。
- `GuardStmt`（`else` を持たない `if`）は、ブロックの末尾文が `ReturnStmt` である場合にのみ許される（6.4）。
- `ReturnStmt` の後に同一ブロックの文を置いてはならない（到達不能。構文エラー）。

継続分配変換（正規化）:

`return` は次の変換で `choose` を用いる式へ正規化される。`C...` は同一ブロックの後続文（継続）を表す。

- `do { A...; return e }` は `do { A...; e }` と同値である。
- `do { A...; if (c) { B...; return e }; C... }` は `do { A...; choose(c, \() -> do { B...; e }, \() -> do { C... }) }` へ変換される。
- 文位置の `if (c) { X... } else { Y... }` の分岐に `return` が含まれる場合、後続文 `C...` を両分岐へ注入して同様に変換する（`return` で終わる分岐は継続を捨て、終わらない分岐は末尾に継続を接続する）。
- 変換は最も内側のブロックから再帰的に適用する。変換後の式に `return` は残らない。

型規則（早期終了）:

- すべての `return e` の式 `e` と、関数本体の最終値は、同一の型 `T`（関数の戻り値型）を持たなければならない。継続分配変換後の式に対する既存の型規則（6.4 の分岐型一致）がこれを保証する。
- `GuardStmt` を関数本体の末尾文に置いた場合、継続が空となるため、戻り値型が `Void` の場合を除き型エラーとなる。

型規則:

- `BindStmt` は右辺 `Expression` が型付け可能であれば型付け可能とする。
- `ExprStmt` は任意の型 `T` で型付け可能だが、文脈上その値は次文へ渡さない。
- `do` 全体の型は、最後の文（末尾 `ExprStmt` またはそれに等価な式）の型とする。文を 1 つも持たない場合は `Void` とする。
- 空のブロック（`do {}`、および 6.4 の `IfExpr` / `ForExpr` の空の `Block` を含む）は許可する。空のブロックの型は `Void` とし、評価結果は `Void` とする。
- `BindStmt` の右辺が `Void` 型の場合も束縛自体は可能だが、束縛された名前を値として参照することはできない（4.4）。
- `IfExpr` / `ForExpr` の型規則は 6.4 に従う（`BindStmt` の右辺や末尾文として出現した場合も同じ）。

評価規則:

- `do` 内の文は必ず上から下へ評価する。
- `BindStmt` の右辺評価が失敗した場合、その時点で `do` 全体は失敗し、後続文は評価しない。
- `IfExpr` / `ForExpr` の評価規則は 6.4 に従う。

スコープ規則:

- `do` ブロック内で `BindStmt` により導入された識別子は、その文より後ろの同一ブロック内で有効とする。
- `if` / `for` のブロック（6.4）内の束縛は、そのブロックの外側へ漏れない。
- `for (x : xs)` の反復変数 `x` は本体ブロック内でのみ有効とする。

記述例:

```lask
build() = do {
  image = "app"
  tag = "latest"
  $ docker build -t #{image}:#{tag} .
  "ok"
}

classify(n: Number) = do {
  if (n > 0) {
    "pos"
  } else {
    "non-pos"
  }
}

labels(xs: Array<String>) = do {
  for (x : xs) {
    concat("item:", x)
  }
}

publish(tag: String): String = do {
  if (tag == "") { return "skip: no tag" }
  r = $* ./release.sh #{tag}
  if (r.code != 0) { return r.stderr }
  "released"
}
```

### 6.6 コマンド実行式

```ebnf
CommandExpr  = "$" [ stream ] [ "[" Expression "]" ] shell_string .
stream       = "1" | "2" | "*" .
shell_string = { shell_char | interpolation } .
shell_char   = unicode_char .
```

ここで `shell_char` は `unicode_char`（3 章の共通字句要素。改行を含まない）とする。コマンド文字列は行末で終端する（詳細は本節の字句規則に従う）。

コマンド実行式は、シェルコマンド実行を簡潔に記述するための糖衣構文である。
意味論上は組み込み関数 `runCommand` へ正規化して扱う。ストリーム指定子 `1`・`2`・`*` はファイルディスクリプタ番号に由来し、コマンドの結果のどこを受け取るかを選ぶ（`1` = 標準出力、`2` = 標準エラー、`*` = 結果全体）。

関数としての定義:

- `runCommand` は、指定した実行環境でコマンドを実行し、結果全体（終了コード・標準出力・標準エラー）を返すコア関数である。
- 署名は `runCommand(cmd: String, --env: Environment = #local): CommandResult` とする。実行環境はキーワードパラメータ `env` で与え、未指定時は既定実行環境 `#local` で補完される（10.1）。
- `runCommand` は、コマンドが完了すれば終了コードに関わらず成功する（8.7）。失敗となるのは実行基盤系の障害（環境解決不能、接続不能、コマンド起動不能等）のみである。

`CommandResult` 型:

- `type CommandResult = Record<code: Number, stdout: String, stderr: String>` を組み込みの型エイリアスとして定義する。`CommandResult` はユーザー定義の型エイリアスや値宣言で上書きしてはならない。
- `code` はコマンドの終了コード、`stdout`・`stderr` は各ストリームの内容である。構成規則は 8.7 に従う。

糖衣規則:

- `$* cmd` は `runCommand("cmd")` の糖衣である。
- `$ cmd` および `$1 cmd` は、次の式の糖衣である（`r` は他と衝突しない新鮮な識別子）。

  ```lask
  do {
    r = runCommand("cmd")
    if (r.code == 0) { r.stdout } else { fail({code: r.code, message: r.stderr}) }
  }
  ```

- `$2 cmd` は、上記の成功分岐を `r.stderr` に置き換えた式の糖衣である。
- 環境指定 `$[env]`・`$1[env]`・`$2[env]`・`$*[env]` は、それぞれの展開形の `runCommand` へ `env = env` を渡す。
- 展開形に現れるのはコア関数（`runCommand`、`fail`、`choose` への正規化）とレコードリテラルのみであり、ユーザー定義によって挙動が変わることはない。
- `shell_string` 内の `#{e}` は文字列補間として先に評価し、補間後文字列をコマンド本体として渡す。

字句規則:

- コマンド文字列は、`$`（ストリーム指定子がある場合はその直後、環境指定がある場合は閉じ `]`）の直後から行末までとする。改行がコマンド文字列の終端であり、3.3 の改行トークンとして扱う。ストリーム指定子・環境指定は `$` に空白を挟まず続けなければならない。
- コマンド文字列の先頭・末尾の空白は除去し、内部の空白はそのまま保持する。
- 行末が `\` の場合は継続行とし、`\` と改行を取り除いた上で次の行を連結する。
- コマンド文字列内では、シェルの `;`、引用符、パイプ等をエスケープなしで使用できる。
- `#{` は補間開始とする。リテラルの `#{` を含める場合は `\#{` と書く。`{` が後続しない `#` はそのまま文字として扱う。
- `do` 内では、コマンド文字列を終端する改行が同時に文終端（6.5）を兼ねる。
- コマンド文字列は改行で必ず終端するが、囲む式は 6.5 の継続規則に従って次行の二項演算子で継続できる。例えば `$ git --version` の次行に `|> trim` を置くと、`runCommand("git --version") |> trim` と解釈される。
- コマンド実行式と同一行のそれ以降のトークンは、すべてコマンド文字列の一部となる。したがって同一行に式の後続トークン（閉じ括弧等）を置くことはできない。式の内部で加工する場合は、いったん束縛してから利用するか、`runCommand` を直接呼び出す。

ここで `runCommand` はコア関数であり、ユーザーコードから直接宣言・上書きしてはならない（15.5）。

環境指定規則:

- `Environment` は 4.1 で定義される基本型であり、実行環境の責務は 10 章で定義する。
- `env` は `Environment` 型の式である。通常は環境式（6.7）`#local`、`#docker(...)`（糖衣 `#image-name` を含む）、`#env(...)` で構成するが、`Environment` 値を返す任意の式（変数参照等）を置ける。
- `env` の解決に失敗した場合は実行前エラーとする。
- 既定実行環境（`$ ...` / `runCommand` が用いる環境）は常に `#local` とする（10.1）。
- 環境の詳細な解決規則と責務は 10 章に従う。

型規則:

- `runCommand` は `Function<String, CommandResult>` として型付けする（キーワードパラメータ `env` は関数型に現れない。7.5）。
- 糖衣展開の結果、`$ ...`・`$1 ...`・`$2 ...` の式型は `String`、`$* ...` の式型は `CommandResult` とする。
- `env` が `Environment` に適合しない場合は型エラーとする。
- 補間 `#{e}` は文字列化可能な型でなければならない。文字列化できない場合は型エラーとする。

評価規則:

- 評価は糖衣展開後の式の規則（8.3, 8.7）に従う。コマンド文字列（補間を含む。左から右へ評価）が先に確定し、続いて `env` が評価される。
- `$* ...` はコマンドの完了後、終了コードに関わらず `CommandResult` を返す。
- `$ ...`（`$1 ...`）と `$2 ...` は、終了コード `0` のとき選択したストリームの内容を返す。非 0 のときは展開形の `fail` により失敗となり、`Error` 値（`code` = コマンドの終了コード、`message` = 標準エラー出力の内容）が `try`/`catch`（6.9）で捕捉できる。捕捉されない場合、コマンドの終了コードがそのままプロセスの終了コードとなる（8.10, 11.3）。
- 標準入力、標準出力、標準エラーの取り扱いは 9 章の入出力契約に従う。

セキュリティと可搬性の注意:

- 補間値をコマンドへ埋め込む場合、実装は安全なエスケープ戦略を提供すべきである。
- シェル方言差異は実行環境依存とし、仕様はコマンド文字列の評価手順のみを規定する。

記述例:

```lask
show_version() = do {
  v = $ git --version
  v
}

build_in_docker(env: Environment) = do {
  out = $[env] sh -lc 'echo inside-container'
  out
}

show_in_fixed_image() =
  $[#alpine:3.20] uname -a

lint(): String = do {
  r = $* golangci-lint run
  if (r.code == 0) { "clean" } else { r.stdout }
}
```

### 6.7 環境式

```ebnf
EnvExpr     = env_head [ EnvArgList ] .
EnvArgList  = "(" [ EnvArgument { "," EnvArgument } ] ")" .
EnvArgument = [ lower_id "=" ] Expression .
```

環境式は、コマンド実行先（10 章）を `#環境種別(引数...)` の形式で値として構成する式であり、式の型は常に `Environment` とする。環境種別ごとの引数は、関数と同一のパラメータ規則（6.1: 位置束縛・既定値）で定義された環境コンストラクタ署名（10.2）に対して与える。

構文規則:

- `env_head` は 3.3 で定義する字句トークンであり、`#` に環境種別名または Docker イメージ名が続く。
- `EnvArgList` の開き `(` は、`env_head` の直後に空白を挟まず置かなければならない。空白を挟んだ `(` は環境式の一部とせず、独立した式として解釈する。
- `EnvArgList` を伴う場合、`env_head` の本体（`#` を除いた部分）は `lower_id` に適合する環境種別名でなければならない。適合しない場合（例: `#alpine:3.12(...)`）は構文エラーとする。
- `EnvArgument` は位置引数（`Expression`）または名前付き引数（`lower_id "=" Expression`）とする。位置引数はすべての名前付き引数より前に置かなければならない。
- 環境種別 `env` の引数は、補間を含まない文字列リテラルでなければならない（10.2）。
- 名前付き引数の規則は、関数呼び出しのキーワード引数（6.1, 7.5）と同一とする。名前は環境コンストラクタ署名のキーワードパラメータ名と一致しなければならず、位置パラメータの名前指定および同一パラメータへの重複指定は静的エラーとする（環境式では `E-TYPE-ENV-CONSTRUCT`）。
- `env_char` には `.` を含むため、`env_head` の直後にアクセサ `.` を続けることはできない（トークンに取り込まれる）。加工が必要な場合はいったん変数へ束縛する。

糖衣規則:

- 引数がない場合、`EnvArgList` は省略できる。`#name`（本体が 10.2 の環境種別名に一致）は `#name()` の糖衣である。例: `#local` は `#local()` と同値。
- 本体が環境種別名に一致しない `#image-name` は、`#docker("image-name")` の糖衣である（Docker 糖衣）。例: `#alpine:3.12` は `#docker("alpine:3.12")` と同値。
- したがって、環境種別名と同名の Docker イメージ（例: `local`）を指定する場合は、明示形 `#docker("local")` を用いなければならない。
- `local` / `docker` / `remote` 等の環境種別名は予約語ではない。`#` を伴わない位置では通常の識別子として使用できる。

型規則:

- `EnvExpr` の型は `Environment` とする。
- 引数は、10.2 の環境コンストラクタ署名に対して 7.5 の呼び出し整合性（引数束縛・型適合・既定値補完）と本節の名前付き引数規則で検査する。
- 未知の環境種別、位置引数の欠落、未知の名前付き引数は静的エラーとする（7.7）。

評価規則:

- 引数式は記述順（位置引数、続いて名前付き引数）に左から右へ評価する。
- 評価結果は、環境種別と正規化済みパラメータ集合からなる `Environment` 値とする。実行時の環境解決は 10.4 に従う。
- 引数式の評価が失敗した場合、環境式全体を失敗とする。

記述例:

```lask
e1 = #local
e2 = #alpine:3.12
e3 = #docker("alpine:3.12", memory="4g")
e4 = #ubuntu@sha256:9cee2b382fe2412cd77d5d437d15a93da8de373813621f2e4d406e3df0cf0e7c
e5 = #env("ansible")

run_in(env: Environment): String =
  $[env] uname -a
```

### 6.8 アクセサ式

```ebnf
AccessorExpr = PrimaryExpr "." lower_id | PrimaryExpr "[" Expression "]" .
```

アクセサ式は、レコードのフィールド参照（`.`）と、配列・マップの添字参照（`[...]`）を表す。

モジュール名前空間参照との区別:

- `m.symbol` の形で、先頭の `m` が名前空間インポート（5 章）の名前空間名として解決される場合、式全体は名前解決（7.2 の第 4 順位）として扱い、アクセサ式ではない。
- 名前空間名と同名のローカル束縛が存在する場合は 7.2 の優先順位に従う（ローカル束縛が優先され、その場合はフィールドアクセスとして型検査される）。
- 上記以外の `.` はフィールドアクセスとして解釈する。

フィールドアクセスの型規則:

- `e.f` は、`e` の型が `Record<..., f: T, ...>`（フィールド `f` を持つレコード型）のときのみ型付け可能とし、式の型は `T` とする。
- 対象のレコード型がフィールド `f` を持たない場合、および対象の型が `Record` 以外（`Map`、`Any` を含む）の場合は静的エラー（`E-TYPE-ACCESS`）とする。`Any` の値は `cast`（15.8）で具体型へ移行してから参照する。
- `.f` で参照できるのは識別子形（`lower_id`）のフィールド名のみである。`lower_id` に適合しないフィールド名（4.2）は文字列リテラル添字（後述）で参照する。
- `Map` の値取得は `[...]` または `get`（15.4）を用いる。`Record` のフィールド集合は静的に確定している（4.4）ため、フィールドアクセスは実行時に失敗しない。

添字アクセスの型規則:

- `e[i]` は、`e: Array<T>` かつ `i: Number` のとき型付け可能とし、式の型は `T` とする。添字は 0 始まりとする。
- `e[k]` は、`e: Map<T>` かつ `k: String` のとき型付け可能とし、式の型は `T` とする。
- `e[k]` は、`e` の型が `Record<...>` かつ `k` が補間を含まない文字列リテラルであり、その文字列がフィールド名に一致するときも型付け可能とし、式の型は該当フィールド型とする。`e.f` と `e["f"]` は同一フィールドを参照する。
- レコードに対する文字列リテラル以外の添字式、およびフィールド名に一致しない文字列リテラルは静的エラー（`E-TYPE-ACCESS`）とする（キー集合が静的に確定しているため、動的キーには `Map` を用いる）。
- 上記以外の対象型・添字型の組み合わせは静的エラー（`E-TYPE-ACCESS`）とする。

評価規則:

- 評価手順と失敗契約（添字範囲外・キー不在の実行時エラー）は 8.9 で定義する。
- `m[k]` は `get(m, k)` と同一の失敗契約を持つ。

記述例:

```lask
user = {name: "alice", age: 20}
userName = user.name

xs = [10, 20, 30]
first = xs[0]

envMap: Map<String> = {"APP_ENV": "prod"}
appEnv = envMap["APP_ENV"]

hdrs = {"X-Api-Key": "secret"}
apiKey = hdrs["X-Api-Key"]
```

### 6.9 エラー処理式

```ebnf
TryExpr       = "try" Block ( CatchClause [ FinallyClause ] | FinallyClause ) .
CatchClause   = "catch" "(" lower_id ")" Block .
FinallyClause = "finally" Block .
```

エラー処理式は、評価中の失敗（実行時エラー・外部 I/O エラー）を捕捉して代替計算へ合流させる式である。意味論上はコア関数 `recover` と `fail` へ正規化して扱う。

`Error` 型:

- `type Error = Record<code: Number, message: String>` を組み込みの型エイリアスとして定義する。`Error` はユーザー定義の型エイリアスや値宣言で上書きしてはならない。
- `code` は終了コード、`message` は人間可読メッセージを表す。失敗から `Error` 値への写像（コマンドの終了コード・標準エラーの引き継ぎを含む）は 8.10 で定義する。

関数としての定義:

- `recover` は本体関数とハンドラ関数を受け取り、本体の失敗を捕捉してハンドラへ合流させるコア関数である。
- `fail` は `Error` 値を受け取り、その失敗を送出するコア関数である。ハンドラ内での再送出、およびユーザー定義エラーの送出に用いる。
- `error` はエラー値の構築補助関数である（15.7）。

ここで `recover` と `fail` はコア関数であり、ユーザーコードから直接宣言・上書きしてはならない。

糖衣規則:

- `try B catch (e) H` は `recover(\() -> do { B }, \(e) -> do { H })` の糖衣である。
- `try B finally F` は `do { v = recover(\() -> do { B }, \(e) -> do { F; fail(e) }); F; v }` の糖衣である（`v` は他と衝突しない新鮮な識別子）。`F` は成功・失敗のどちらの経路でも正確に 1 回評価される。
- `try B catch (e) H finally F` は `try (try B catch (e) H) finally F` と同値である（`catch` を先に適用し、その全体へ `finally` を適用する）。

型規則:

- `recover` は `Function<Function<T>, Function<Error, T>, T>` として型付けする。
- `fail` は `Function<Error, T>` として型付けする。戻り型 `T` は組み込み多相（4.4）により文脈の期待型から具体化する。
- `catch` を持つ `TryExpr` は、本体ブロックと `catch` ブロックの型が同一の `T` である場合にのみ型付け可能とし、式全体の型は `T` とする。
- `catch (e)` の `e` は `Error` 型として `catch` ブロック内でのみ有効とする。
- `finally` ブロックの型は任意とし、その値は捨てられる。`try B finally F` の式型は本体ブロックの型とする。

捕捉規則:

- 捕捉対象は、本体ブロックの評価中に発生した実行時エラーおよび外部 I/O エラーである。構文・静的エラーは評価前に検出されるため対象外とする。
- `catch` ブロック・`finally` ブロック内で発生した失敗は、同じ `TryExpr` では捕捉されず外側へ伝播する。
- `TryExpr` が入れ子の場合、最内の `TryExpr` が先に捕捉する。

記述例:

```lask
build(): String = do {
  out = try {
    $ make build
  } catch (e) {
    if (e.code == 2) {
      $ make clean
      $ make build
    } else {
      fail(e)
    }
  } finally {
    $ rm -rf ./tmp
  }
  out
}
```

## 7. 静的意味論

本章では、実行前に検証可能な意味論を定義する。

静的検証は次の順で行う。

1. モジュール依存解決（循環検出を含む）
2. トップレベルシンボル表構築
3. 名前解決
4. 型注釈整合と型推論
5. 呼び出し整合性検査

### 7.1 検証コンテキスト

静的検証では、次の 3 種の環境を用いる。

- モジュール環境 `M`: インポート解決済みモジュール集合
- 型環境 `Δ`: 型エイリアスと型名解決情報
- 値環境 `Γ`: 変数・関数・パラメータの型束縛

型判断は `Γ ⊢ e : T` の形で表す。

### 7.2 名前解決順

識別子は次の優先順位で解決する。

1. 最内側ローカル束縛（ラムダ引数、`do` 束縛、`for` 反復変数）
2. 現在モジュールのトップレベル宣言
3. 名前付きインポートで取り込まれたシンボル（改名後の名前）
4. 名前空間インポートの `namespace.symbol` 参照
5. 組み込みライブラリのシンボル（15 章）および予約済み識別子 `stdin`（9.3）

解決規則:

- 同一優先順位で候補が複数ある場合は曖昧参照エラーとする。
- どの優先順位にも候補がない場合は未定義参照エラーとする。
- 予約語は識別子として束縛してはならない。
- 組み込みライブラリのシンボルは最下位（第 5 順位）で解決されるため、ユーザー定義の同名シンボルが常に優先される（シャドーイング。15.1）。
- ただし、上書き禁止と規定されたコア関数名（`spawn`、`choose`、`map`、`filter`、`reduce`、`forEach`、`runCommand`、`recover`、`fail`。6 章）および `stdin`（9.3）は、第 1〜4 順位のいずれの位置でも宣言・束縛してはならない。違反は重複定義エラー（`E-NAME-DUPLICATE`）とする。

### 7.3 スコープとシャドーイング

スコープ規則:

- ラムダパラメータはラムダ本体でのみ有効。
- `do` の `BindStmt` は、宣言文より後続の同一ブロック内で有効。
- `if` / `for` / `try` ブロック内の束縛は外側へ漏れない。
- `for (x : xs)` の `x` は反復本体でのみ有効。
- `catch (e)` の `e` は `catch` ブロック内でのみ有効。

シャドーイング規則:

- 内側スコープから外側スコープの同名束縛を隠すことは許可する。
- 同一スコープ内の同名再束縛は重複定義エラーとする。
- トップレベルでは同名の値宣言・関数宣言を重複してはならない。

### 7.4 型注釈と推論の統合

型注釈と推論の関係は次の通り。

- 注釈がある場合は注釈型を期待型として検証する。
- 注釈がない場合は 4.3 の規則で推論する。
- 推論結果の型が注釈型に適合（4.4）しない場合は型不一致エラーとする。

補足規則:

- `NamedType` は検査前に `TypeAliasDecl` へ展開する。
- オーバーロードは許可しないため、1 シンボルは 1 関数型のみ持つ。
- `Any` は受け入れ側で広く許容される（任意の型が `Any` に適合する）が、`Any` から具体型への移行は `cast`（15.8）による実行時型検査でのみ行える（4.4）。

### 7.5 呼び出し整合性

呼び出し `f(a1, ..., an)` は、`f` が `Function<T1, ..., Tm, R>` に解決されるときのみ型付け可能とする。

宣言パラメータ情報:

- 関数宣言・ラムダ式のパラメータは、位置パラメータ（すべて必須。個数を `m` とする）、高々 1 つの可変長パラメータ、およびキーワードパラメータ集合（名前・型・既定値式）からなる（6.1）。
- 関数型 `Function<T1, ..., Tm, R>` の型引数列には、位置パラメータ（および可変長パラメータの配列型）のみが現れる。パラメータ名・キーワードパラメータ・可変長性は関数型には含まれず、宣言に付随する静的情報（宣言パラメータ情報）として保持する。キーワード束縛・既定値補完・可変長収集はいずれもこの情報に依存し、呼び出し先が宣言へ静的に解決できる場合にのみ利用できる。

検証項目（引数束縛）:

- `f` が関数宣言またはラムダ式へ静的に解決される場合、引数は次の手順でパラメータへ束縛する。
  1. 位置引数を宣言順の位置パラメータへ先頭から束縛する。位置引数が `m` 個に満たない場合は `E-TYPE-ARITY` とする。
  2. `m` 個を超える位置引数は、可変長パラメータがあれば記述順に収集して 1 つの配列として束縛し（可変長収集）、なければ `E-TYPE-ARITY` とする。可変長パラメータに対応する位置引数が 0 個の場合は空配列を束縛する。
  3. キーワード引数を、名前が一致するキーワードパラメータへ束縛する。未知の名前、位置パラメータ・可変長パラメータの名前指定、および重複束縛は `E-TYPE-KEYWORD` とする（6.1）。
  4. 束縛されなかったキーワードパラメータは、8.3 の規則に従い呼び出し時に既定値式で補完する（既定値補完）。
- `f` が関数型の値としてのみ解決される場合（関数型パラメータへの適用、式の評価結果の適用、`Function<...>` 注釈のみの値等）、宣言パラメータ情報を参照できないため、位置引数のみで位置パラメータ全体の明示（`n = m`）を要求する。キーワード引数の使用は `E-TYPE-KEYWORD` とし、キーワードパラメータはすべて既定値で補完される。

検証項目（型と結果）:

- 束縛された各引数が、対応するパラメータ位置の型 `Ti` に適合すること
- 結果型を `R` として後続式へ受け渡せること

補助関数（糖衣の正規化先）の整合:

- `spawn`: `Function<Function<T>, AsyncHandle<T>>`
- `await`: `Function<AsyncHandle<T>, T>`
- `choose`: `Function<Bool, Function<T>, Function<T>, T>`
- `map`: `Function<Array<T>, Function<T, U>, Array<U>>`
- `filter`: `Function<Array<T>, Function<T, Bool>, Array<T>>`
- `reduce`: `Function<Array<T>, U, Function<U, T, U>, U>`
- `forEach`: `Function<Array<T>, Function<T, U>, Void>`
- `recover`: `Function<Function<T>, Function<Error, T>, T>`
- `fail`: `Function<Error, T>`
- `runCommand`: `Function<String, CommandResult>`（キーワードパラメータ `--env: Environment = #local` を持つ）

署名中の型変数（`T`、`U` 等）は 4.4 の組み込み多相規則に従い、呼び出しごとに具体化して検査する。

`async` / `if` / `for` / `$ ...` は、上記補助関数への糖衣として静的検証する。`await e` はコア関数 `await` の適用として検証する。

環境式の整合:

- 環境式 `#kind(args)`（6.7）の引数は、10.2 の環境コンストラクタ署名に対して本節と同じ検証項目（引数束縛・型適合・既定値補完）を適用する。環境コンストラクタ署名は常に宣言として静的に解決されるため、既定値補完と名前付き引数は常に使用できる。
- 名前付き引数に関する違反（未知の名前・重複束縛）は、環境式では `E-TYPE-ENV-CONSTRUCT` として報告する（7.7）。

### 7.6 構文糖衣の静的展開順

静的検証時の展開順は次の通り。

1. `async e` -> `spawn(\() -> e)`
2. `await e` -> コア関数適用 `await(e)`（括弧省略形の正規化）
3. `return`（ガード文を含む）の継続分配変換（6.5）
4. `if (c) { ... } else { ... }` -> `choose(c, \() -> do { ... }, \() -> do { ... })`
5. `for (x : xs) { ... }` -> `map(xs, \(x) -> do { ... })`（本体ブロックの型が `Void` の場合は `forEach(xs, \(x) -> do { ... })`。6.4）
6. `try ... catch (...) { ... }` / `finally { ... }` -> `recover` / `fail` を用いる式への展開（6.9）
7. `do { ... }` の逐次実行展開
8. 環境式糖衣の展開（`#name` -> `#name()`、環境種別名以外の `#image-name` -> `#docker("image-name")`）
9. `$ cmd` / `$[env] cmd` のコマンド糖衣展開

展開後のコア式に対して型検査を行う。展開結果と元構文の意味は同値でなければならない。

手順 5 の展開先選択（`map` / `forEach`）のみ、本体ブロックの型に依存する（型指向展開）。実装は本体ブロックの型付けを先行して行い、その結果で展開先を確定する。他の展開はすべて純構文的である。

### 7.7 静的エラー

静的検証で報告するエラー種別は少なくとも次を含む。

- `E-NAME-UNDEFINED`: 未定義参照
- `E-NAME-AMBIGUOUS`: 曖昧参照
- `E-NAME-DUPLICATE`: 重複定義
- `E-TYPE-MISMATCH`: 型不一致
- `E-TYPE-ARITY`: 関数引数個数不一致（位置引数の不足・超過。7.5）
- `E-TYPE-KEYWORD`: キーワード引数不正（未知の名前、位置・可変長パラメータの名前指定、重複束縛、関数型値への適用。6.1, 7.5）
- `E-TYPE-CALL`: 呼び出し不正（非関数値呼び出し等）
- `E-TYPE-COMMAND-ENV`: コマンド実行環境型不正
- `E-TYPE-ENV-CONSTRUCT`: 環境式・環境定義不正（未知の環境種別、位置引数の欠落、未知または重複の名前付き引数、`env` の非リテラル引数、環境定義ファイルの不正・未定義の環境名。10.3）
- `E-TYPE-ACCESS`: アクセサ不正（`Record` 以外へのフィールドアクセス、未知フィールド、不正な添字型）
- `E-TYPE-FIELD-DUPLICATE`: レコードフィールド名・オブジェクトリテラルキーの重複（4.2）
- `E-TYPE-ILLFORMED`: 型の整形規則違反（`Void` の不正位置、再帰型エイリアス、`cast` の不正な対象型。4.2, 15.8）
- `E-MODULE-CYCLE`: モジュール循環依存

エラー診断には、少なくとも次を含める。

- エラーコード
- 位置情報（行・列またはスパン）
- 期待型と実際型（該当時）
- 解決候補（曖昧参照時）

## 8. 動的意味論

本章では、式の評価順序と実行時の意味を定義する。

動的意味論は、7.6 で静的展開されたコア式を対象に定義する。
評価結果は「成功値」または「失敗」のいずれかである。

### 8.1 評価関係

評価関係を次で表す。

- `⟨ρ, A, e⟩ ⇓ v`: 環境 `ρ` と非同期状態 `A` の下で、式 `e` が値 `v` に評価される。
- `⟨ρ, A, e⟩ ⇑ err`: 環境 `ρ` と非同期状態 `A` の下で、式 `e` が失敗 `err` で停止する。

ここで `ρ` は値束縛環境、`A` は `AsyncHandle` の状態集合（実行中・成功・失敗）とする。

評価順序の原則:

- 関数引数は左から右へ評価する。
- 配列・レコード要素も左から右へ評価する。
- 短絡演算（`&&`, `||`）は 6.2 の規則に従う。

### 8.2 値とクロージャ

実行時値には少なくとも次を含む。

- 基本値（`Number`, `String`, `Bool`, `Null`）
- 環境値 `Environment`（環境種別と正規化済みパラメータ集合）
- 配列値、マップ値、レコード値
- 関数クロージャ（ラムダ本体と定義時環境）
- 非同期ハンドル値 `AsyncHandle<T>`

関数値はクロージャとして評価され、自由変数は定義時環境で束縛される。

### 8.3 関数適用

`f(a1, ..., an)` の評価手順は次の通り。

1. `f` を評価し、関数クロージャであることを確認する。
2. 引数を記述順（位置引数、続いてキーワード引数の記述順）に左から右へ評価する。
3. 位置引数を宣言順の位置パラメータへ、位置パラメータ数を超える分を可変長パラメータの配列要素へ（評価順を保持）、キーワード引数を名前が一致するキーワードパラメータへ束縛する（7.5）。
4. キーワードパラメータの既定値式は、対応する引数が与えられない場合にのみ評価する。
5. 関数本体を拡張環境で評価し、その結果を返す。

デフォルト引数規則:

- 既定値式は呼び出し時に評価する（定義時には評価しない）。
- 既定値式の評価環境は、先行して束縛された引数を含む。
- 既定値式の評価が失敗した場合、関数呼び出し全体を失敗とする。

### 8.4 `do` の逐次実行

`do { s1; s2; ...; sn }` は上から順に評価する（文区切りの `;` は改行と同義である。6.5 参照）。

- `BindStmt` は右辺を評価して識別子へ束縛し、後続文へ環境を引き継ぐ。
- `ExprStmt` は式を評価して値を捨てる（末尾文を除く）。
- `do` 全体の結果は末尾文の評価結果とする。文を 1 つも持たない場合、結果は `Void` とする。
- 途中文が失敗した場合、後続文は評価せず `do` 全体を失敗とする。

### 8.5 制御構造（コア関数）

`choose(c, t, f)` の評価:

1. `c` を評価する。
2. `c = true` なら `t()` のみ評価する。
3. `c = false` なら `f()` のみ評価する。
4. 選択されなかった分岐は評価しない。

`map(xs, body)` の評価:

1. `xs` を評価して配列値を得る。
2. 要素を左から右へ走査し、各要素 `xi` に対して `body(xi)` を評価する。
3. 各結果を同順序で配列へ収集して返す。
4. いずれかの反復が失敗した場合、そこで停止して全体を失敗とする。

`filter(xs, pred)` の評価:

1. `xs` を評価して配列値を得る。
2. 要素を左から右へ走査し、各要素 `xi` に対して `pred(xi)` を評価する。
3. 結果が `true` の要素のみを同順序で配列へ収集して返す。
4. いずれかの述語評価が失敗した場合、そこで停止して全体を失敗とする。

`reduce(xs, init, f)` の評価:

1. `xs` を評価して配列値を得る。
2. `init` を評価して累積値の初期値とする。
3. 要素を左から右へ走査し、累積値 `acc` と各要素 `xi` に対して `f(acc, xi)` を評価し、その結果を新しい累積値とする。
4. 走査完了後の累積値を返す。いずれかの適用が失敗した場合、そこで停止して全体を失敗とする。

`forEach(xs, body)` の評価:

1. `xs` を評価して配列値を得る。
2. 要素を左から右へ走査し、各要素 `xi` に対して `body(xi)` を評価し、結果を捨てる。
3. 走査完了後に `Void` を返す。
4. いずれかの反復が失敗した場合、そこで停止して全体を失敗とする。

### 8.6 非同期（コア関数）

`spawn(thunk)` の評価:

1. `thunk` を関数値として評価する。
2. 新しいハンドル `h` を生成し、`A[h] = running` とする。
3. `thunk()` を非同期実行へ投入する。
4. 呼び出し元には直ちに `h` を返す。

非同期タスク終了時:

- 正常終了時は `A[h] = success(v)`。
- 失敗時は `A[h] = failure(err)`。

`await(h)` の評価:

1. `h` を評価する。
2. `A[h] = running` なら完了まで待機する。
3. `A[h] = success(v)` なら `v` を返す。
4. `A[h] = failure(err)` なら `err` を再送出する。

同一 `h` への複数回 `await` は同一の完了結果を返す。

### 8.7 コマンド実行（コア関数）

`runCommand(cmd, env = ...)` の評価:

1. `cmd` を文字列へ評価する（補間を含むコマンド糖衣では、補間式を左から右へ評価して確定した文字列が渡される）。
2. `env` を評価する。未指定の場合は既定値 `#local` で補完する（7.5）。
3. `env` を実行環境へ解決する（10.4）。
4. 解決した環境でコマンドを同期実行する。実行中、子プロセスの標準出力・標準エラーは 12.3 の規則で stderr へリアルタイムに中継される（中継は評価結果に影響しない）。
5. コマンドの完了後、`CommandResult` 値（6.6）を構成して返す。終了コードに関わらず成功とする。

`CommandResult` の構成規則:

- `code`: プロセスの終了コードをそのまま設定する。シグナルによる終了は、シェル慣行（`128 + シグナル番号`）に従って写像してよい。
- `stdout` / `stderr`: 各ストリームの内容を設定する（実装定義のサイズ上限まで。超過時は先頭・末尾を保持する要約としてよい）。
- 実行基盤系の障害（環境解決不能、接続不能、コマンド起動不能等）の場合のみ、`runCommand` は失敗する（外部 I/O エラー。14 章）。

非 0 終了による失敗の `Error` 値化（終了コード・標準エラー出力の引き継ぎ）は 8.10 に従う。

### 8.8 環境式の評価（コア式）

環境式 `#kind(args)`（6.7）は、糖衣展開（7.6）後も残るコア式であり、次の手順で評価する。

1. 引数式を記述順（位置引数、続いて名前付き引数）に左から右へ評価する。
2. 評価値を環境コンストラクタ署名（10.2）のパラメータへ束縛し、与えられなかったキーワードパラメータは既定値式を評価して補完する（8.3 のデフォルト引数規則と同一）。
3. 環境種別と正規化済みパラメータ集合からなる `Environment` 値を返す。
4. 引数式または既定値式の評価が失敗した場合、環境式全体を失敗とする。

環境値の実行環境への解決（10.4）は、環境式の評価時ではなく `runCommand` によるコマンド起動の直前に行う。

等価比較:

- `Environment` 値に対する `==` / `!=`（6.2）は、環境種別と正規化済みパラメータ集合の構造的一致で判定する。

### 8.9 アクセサ式の評価（コア式）

フィールドアクセス `e.f` の評価:

1. `e` を評価してレコード値を得る。
2. フィールド `f` の値を返す。フィールドの存在は静的検証（6.8）で保証されるため、この段階で失敗しない。

添字アクセス `e[i]` の評価:

1. `e` を評価する。
2. `i` を評価する。
3. `e` が配列値の場合: `i` が非負整数かつ要素数未満であれば該当要素を返す。非整数・負数・範囲外は実行時エラー（`E-RUNTIME-ACCESS`）とする。
4. `e` がマップ値の場合: キー `i` が存在すれば対応する値を返す。不在の場合は実行時エラー（`E-RUNTIME-ACCESS`）とする。`get(m, k)`（15.4）と同一の失敗契約とする。
5. `e` がレコード値の場合: 添字は文字列リテラルに限られ、フィールドの存在は静的検証（6.8）で保証されるため、該当フィールドの値を返す。この段階で失敗しない。

部分式の評価が失敗した場合、アクセサ式全体を失敗とする。

### 8.10 失敗伝播と復旧

失敗伝播規則:

- 部分式が失敗した場合、明示的に捕捉されない限り外側式へ伝播する。
- `choose` は選択された分岐の失敗のみを伝播する。
- `map` / `filter` / `reduce` / `forEach` は最初に発生した失敗を全体失敗として返す。
- `await` は対応する非同期失敗を再送出する。
- `recover` は本体の失敗を捕捉する（本節後述）。ハンドラ内の失敗は捕捉せず伝播する。

`Error` 値化規則:

失敗を捕捉するとき、およびトップレベルへ到達したとき、失敗は次の規則で `Error` 値（6.9）へ写像される。

- 実行時エラー: `code` は `2` とする（11.3 の終了コード分類と同じ値）。
- 外部 I/O エラー: `code` は `3` とする（同上）。
- `fail(err)` による失敗: 与えられた `err` をそのまま用いる。コマンド実行式 `$`・`$1`・`$2` の非 0 終了に起因する失敗はこの場合に該当し、糖衣展開（6.6）により `code` = コマンドの終了コード、`message` = 標準エラー出力の内容となる（シグナル写像・取り込み上限は 8.7 の `CommandResult` 構成規則に従う）。
- `message` に含まれる秘密情報は、12.8 の規則に従いマスクまたは除去する。

`recover(body, handler)` の評価:

1. `body()` を評価する。
2. 成功した場合はその値を返す。`handler` は評価しない。
3. 失敗した場合は失敗を `Error` 値 `err` へ写像し、`handler(err)` を評価してその結果を返す。
4. `handler` の評価中の失敗は、この `recover` では捕捉せず外側へ伝播する。

`fail(err)` の評価:

1. `err` を評価して `Error` 値を得る。
2. その `Error` 値を持つ失敗を送出する。

未捕捉失敗の終了規則:

- トップレベル（CLI が起動した評価の最外殻）まで伝播した失敗は、`Error` 値化されたうえでプロセスを終了させる。プロセスの終了コードは `Error` 値の `code` とする（11.3, 14.8）。
- 終了コードへ反映する際、`code` が 1〜255 の整数でない場合（0、負数、非整数、255 超）は `1` へ正規化する。`Error` 値そのものは変更しない。
- stderr へのエラー診断出力は 14 章に従う。

## 9. 標準入出力とデータフロー

本章では、標準入力・標準出力・標準エラーと関数間データ受け渡しを定義する。

### 9.1 入出力チャネルモデル

Lask 実行系は、少なくとも次の 3 つのチャネルを区別して扱わなければならない。

- 標準入力（stdin）: 実行開始前に外部から受け取る入力データ
- 標準出力（stdout）: 評価結果（`eval`。9.5）を出力するチャネル
- 標準エラー（stderr）: 診断・障害情報を出力するチャネル

チャネル分離規則:

- 実装は stdout と stderr を論理的に分離しなければならない。
- 主結果は stdout、診断情報は stderr へ出力しなければならない。
- コマンド実行式（6.6）で得られる子プロセス出力は、8.7 の規則に従って値化されて式評価へ戻ると同時に、コマンド実行ログとして stderr へリアルタイムに中継される（12.3）。

### 9.2 標準入力の取り込み

標準入力の取り込みは、`run` / `eval` を対象とし、関数評価開始前に次の手順で行う。
`repl` は stdin を対話入力チャネルとして用いるため、本節の取り込みを行わず、`stdin` 参照変数（9.3）も束縛しない。

1. stdin を EOF まで読み取る。
2. 読み取った入力全体を 1 つの入力スナップショットとして固定する。
3. 入力スナップショットを 9.4 の規則で UTF-8 文字列へデコードし、`String` 値を生成する。
4. 変換結果を 9.3 の参照変数へ束縛してから関数評価を開始する。

規則:

- 実行中に stdin を追加受信して評価へ反映する動作は、本仕様の対象外とする。
- stdin が空の場合も成功ケースとして扱い、空文字列 `""` として値化する。
- EOF 取得前に I/O 障害が発生した場合は実行時エラーとする。

### 9.3 標準入力参照変数

実行系は、デコード済み標準入力へアクセスするための読み取り専用参照変数 `stdin` を提供しなければならない。

規則:

- `stdin` は予約済み識別子として扱い、ユーザー定義で再束縛してはならない。
- `stdin` の束縛は実行単位ごとに 1 回だけ確定する。
- `stdin` の可視性は評価開始時のトップレベル環境から有効とし、通常の名前解決規則（7.2）に従って参照可能とする。
- `stdin` は不変値として扱い、破壊的更新を許可しない。
- `repl` では `stdin` を使用できない。束縛が提供されないため、参照は未定義参照エラー（`E-NAME-UNDEFINED`）とする。

型規則:

- `stdin` の静的型は `String` に固定する。実装・CLI 設定によって変更してはならない。
- 行分割や JSON 解釈などの構造化は、言語内で組み込みライブラリの関数を適用して行う（例: `split(stdin, "\n")`（15.3）、`fromJson(stdin)`（15.8））。`fromJson` の結果（`Any`）から具体型への移行には `cast`（15.8）を併用する。

### 9.4 標準入力デコード

標準入力は常に UTF-8 文字列としてデコードし、`String` 値として `stdin` へ束縛する。

規則:

- 入力スナップショットは UTF-8 としてデコードしなければならない。
- 入力の構造化（行分割、JSON 解釈等）を選択する CLI オプションは提供しない。デコード方式が言語外の設定に依存すると、`stdin` の型とプログラムの意味が呼び出しごとに変わるためである。構造化は 9.3 の通り言語内で明示的に行う。

失敗規則:

- UTF-8 としてデコード不能な入力は実行時エラーとする。
- デコードエラーは 14 章の外部 I/O エラー分類（`E-IO-DATA-DECODE`）へ写像されなければならない。

### 9.5 標準出力の役割

標準出力は、評価結果を外部へ受け渡す主チャネルである。

規則:

- `eval` が関数実行を完了したとき、評価結果は指定エンコード方式で stdout へ出力される（11.3）。
- `run` は評価結果を stdout へ出力しない。`run` の主目的はタスクの実行であり、結果の観測は実行ログ・実行イベント（12 章）で行う。
- `eval` の評価結果が `Void` の場合、stdout 出力は空であってよい。
- stdout へは返却値以外を出力してはならない。診断・ログ・子プロセス出力の中継は、すべて stderr へ出力する（9.6, 12.3）。
- 出力エンコード方式の詳細は 11.3 と 13 章に従う。

### 9.6 標準エラーの役割

標準エラーは、実行失敗・警告・診断のための専用チャネルである。

規則:

- stderr はすべてのログの出力先である。少なくとも次を stderr へ出力しなければならない。
  - コマンド実行ログ（子プロセスの標準出力・標準エラーのリアルタイム中継。12.3）
  - 実行ログ（12.2）
  - 構文・静的検証・実行時障害のエラー診断（14 章）
- stderr の内容は、人間可読メッセージに加えて機械可読なエラーコード（14 章）を含んでよい。
- stderr への出力有無は stdout の意味（主結果）に影響を与えてはならない。
- コマンドの標準エラー出力は、stderr への中継（12.3）と並行して、`CommandResult`（8.7）の `stderr` および `$`・`$1`・`$2` の失敗値の `message`（6.6）へ取り込まれる。

### 9.7 関数間データフローとパイプ

Lask におけるデータフローは、関数適用・戻り値・パイプ演算子（6.2）で表現する。

データ受け渡し規則:

- 関数間の値受け渡しは、位置引数・キーワード引数と戻り値によってのみ行う。
- `e |> f` は `f(e)` の糖衣として、左辺結果を右辺関数へ渡す。
- `f >> g` は関数合成を表し、評価時には `f` の結果を `g` へ渡す単一のデータフローとして扱う。
- `map(xs, body)` は要素単位のデータフローを配列へ集約する。副作用目的で結果が不要な場合は `forEach(xs, body)` を用いる。

入出力との接続規則:

- 外部入力から内部式への入口は `stdin` 束縛のみとする。
- 内部式から外部出力への出口は、`eval` における評価結果の stdout 出力（9.5）と、障害・診断時の stderr 出力とする。
- コマンド実行式は、外部プロセス出力を `String` 値として式データフローへ再接続する。

記述例:

```lask
normalize() = do {
  text = stdin
  text
    |> trim
    |> toLower
}

fanout(xs: Array<String>) =
  map(xs, \(x) -> concat("item:", x))
```

## 10. 実行環境

本章では、コマンド呼び出し時に指定できる実行環境とその責務を定義する。

### 10.1 `Environment` 型と環境式

`Environment` は、6.6 の `runCommand` がキーワードパラメータ `env` として受け取る実行先コンテキストを表す組み込み基本型（4.1）とする。`Environment` 値は、環境式（6.7）`#環境種別(引数...)` の評価によってのみ構成される。

規則:

- `Environment` はユーザー定義の型エイリアスや値宣言で上書きしてはならない。
- `Environment` 値は、少なくとも次の 3 系統へ解決可能でなければならない。
  - `#local`（ローカル実行）
  - `#docker(...)`（Docker 実行環境。糖衣 `#image-name` を含む）
  - `#env(...)`（名前付き環境の参照。環境定義ファイル（10.3）で定義された `remote` 等へ解決される）
- `runCommand` の `env` 引数は、評価時点で `Environment` 値へ正規化されていなければならない。
- 既定実行環境（`$ cmd` / `runCommand` が用いる環境。6.6, 8.7）は常に `#local` とする。CLI オプションその他の外部設定によって既定実行環境を変更してはならない。ローカル以外で実行するコマンドは、必ず `$[env]`（または `runCommand` の `env` 引数）で環境を明示する。

型整合:

- `runCommand` の型と署名は 7.5 の定義に従う。
- `Environment` 以外の値を `env` 引数に渡した場合は型エラーとする。

### 10.2 対象環境プロファイルと環境コンストラクタ署名

本仕様が規定する実行環境プロファイルは、環境種別名と環境コンストラクタ署名の組で定義する。署名のパラメータ規則（位置束縛・既定値・型注釈）は関数パラメータ（6.1）と同一とし、呼び出し側は環境式（6.7）で位置引数・名前付き引数を与える。

環境式で使用できる環境種別は `local`・`docker`・`env` の 3 つとする。コードに直接記述できるのは、Lask を実行しているホスト上で完結する環境（`local`、`docker`）に限る。ホストをまたぐ環境（`remote`）は接続先の差異が関数の再利用性を損なうため、環境定義ファイル（10.3）で名前付き環境として定義し、`env` で参照する。

- `local`: 呼び出し元ホスト上でのローカルプロセス実行
  - 署名: `local()`（パラメータなし）
  - 記法例: `#local`（`#local()` の糖衣）
- `docker`: Docker イメージで指定されるコンテナ内実行
  - 署名: `docker(image: String, ...)`。`image` は必須であり、空文字列であってはならない。
  - 実装はキーワードパラメータ（例: `--memory: String = 実装既定`、`--cpus: Number = 実装既定`）を署名へ拡張してよい。未知のパラメータ名は静的エラーとしなければならない（7.7）。
  - 記法例: `#docker("alpine:3.12", memory="4g")`、糖衣 `#alpine:3.12`
- `remote`: SSH 経由のリモートホスト実行
  - 署名: `remote(host: String, --user: String = 実装既定, --port: Number = 22)`。`host` は必須とし、`user` の実装既定は現在ユーザーとする。
  - `remote` は環境式では使用できない。環境定義ファイル（10.3）のエントリとしてのみ構成でき、署名はエントリの `params` の検証に用いる。
- `env`: 環境定義ファイル（10.3）で定義された名前付き環境の参照
  - 署名: `env(name: String)`。`name` は必須とする。
  - `name` の実引数は、補間を含まない文字列リテラルでなければならない。それ以外の式は静的エラー（`E-TYPE-ENV-CONSTRUCT`）とする。これにより、モジュールが参照する名前付き環境の集合は静的に確定する。
  - 記法例: `#env("ansible")`

各プロファイルは、少なくとも次の実行属性を持つ。

- プロセス起動方法
- 作業ディレクトリ解決規則
- 環境変数注入規則
- 権限境界とアクセス制約

実装は追加プロファイル（環境種別と署名の組）を拡張してよいが、上記 3 プロファイルとの互換動作を壊してはならない。

### 10.3 環境定義ファイル

ホストをまたぐ実行環境（`remote`）の接続情報は、Lask コードには記述せず、環境定義ファイルで名前付き環境として定義する。コードは環境種別 `env`（10.2）で名前だけを参照する。これにより、接続先の差異がタスク関数の再利用性へ影響しない。

ファイルの解決:

- 既定のファイル名は `environments.lask.json` とし、モジュール解決の基準ディレクトリ（`main.lask` と同じ位置）から読み込む。
- CLI の `--env-file <path>`（11.1）で読み込むファイルを差し替えられる。差し替えはファイル単位の全置換であり、複数ファイルのマージは行わない。

スキーマ:

```json
{
  "environments": {
    "ansible": {"kind": "remote", "params": {"host": "203.0.113.10", "user": "automation"}},
    "builder": {"kind": "docker", "params": {"image": "golang:1.22"}}
  }
}
```

- トップレベルの `environments` は、環境名からエントリへのマップとする。環境名は `lower_id`（3.2）に適合する文字列でなければならない。
- エントリは `kind`（環境種別名）と `params`（パラメータ集合）を持つ。13.1 の `Environment` メタデータ表現と同じ形である。
- `kind` に指定できるのは具体種別（`local`、`docker`、`remote`）のみとする。`env` の指定（間接参照の連鎖）は静的エラーとする。
- `params` の各キーはパラメータ名で束縛する（データ表現のため、位置パラメータも名前で与える）。位置パラメータの充足、未知のキー名の禁止、キーワードパラメータの既定値補完を 7.5 に準じて検査する。
- 認証情報（パスワード、秘密鍵）をこのファイルへ記述してはならない。認証情報は 10.9 の規則に従い、実行設定・資格情報ストアから供給する。

静的検証:

- モジュールが `#env(...)` を 1 つ以上含む場合、環境定義ファイルは静的検証（7 章）の入力となる。ファイルの不在・構文不正・スキーマ不正・エントリの署名不適合、および参照された名前の未定義は、いずれも静的エラー（`E-TYPE-ENV-CONSTRUCT`）とする。
- `#env` の引数は文字列リテラルに限られる（10.2）ため、モジュールが参照する名前付き環境の集合は静的に確定する。実行前に、利用されるすべての環境を列挙・検証できる（11.4 の `envs`）。
- `#env(...)` を含まないモジュールでは、環境定義ファイルは不要である。

記述例:

```lask
provision(): String =
  $[#env("ansible")] ansible-playbook site.yml
```

### 10.4 環境解決規則

環境解決は `runCommand` によるコマンド起動の直前に行う。

解決手順:

1. `env` 式を評価して `Environment` 値（環境種別と正規化済みパラメータ）を得る。
2. 値の環境種別を分類する。`env` は環境定義ファイルのエントリへ置換したうえで（種別判定規則）、`local` / `docker` / `remote` のいずれかへ分類する。
3. 位置パラメータ（`docker` の `image`、`remote` の `host`）の充足と値制約（`image` 非空等）を検査する。
4. 実行可能な具体ランタイム設定へ正規化する。

種別判定規則:

- 環境式の環境種別名が、そのまま `Environment` 値の環境種別となる（`#local()` は `local`、`#docker(...)` は `docker`、`#env(...)` は `env`）。
- 環境種別 `env` の値は、環境定義ファイル（10.3）の該当エントリの種別・パラメータへ置換して解決する。名前の存在とエントリの妥当性は静的検証済みである（10.3）。置換後の種別に対して以降の規則を適用する。
- 糖衣 `#image-name` は、静的展開（7.6）で `#docker("image-name")` へ展開済みである。
- 未知の環境種別は静的エラー（`E-TYPE-ENV-CONSTRUCT`）であり、実行時の環境解決に到達してはならない。

失敗規則:

- 種別不明およびパラメータ欠落は静的エラー（`E-TYPE-ENV-CONSTRUCT`）であり、本節の実行時解決では発生しない。実行環境の指定手段は言語内の環境式のみである（CLI から実行環境を与える手段は提供しない。11.1）。
- パラメータの値制約違反（空イメージ名等）、または実行基盤不在（Docker デーモン不在、SSH 接続不能等）は実行前エラーとする。
- 解決失敗は 14 章の外部 I/O または実行時エラーへ分類されなければならない。

決定性:

- 同一の `Environment` 値、同一の環境定義ファイルの内容、および同一の実行設定に対して、環境解決結果は決定的でなければならない。

### 10.5 作業ディレクトリ規則

作業ディレクトリ（cwd）はコマンド実行の相対パス解決基準である。

規則:

- `local` の既定 cwd は、実行を開始したプロジェクト基準ディレクトリとする。
- `docker` の既定 cwd は、コンテナ内で実装が定める作業ディレクトリとする。
- `remote` の既定 cwd は、接続先で解決されたユーザー初期ディレクトリまたは実装設定値とする。
- 明示指定がある場合は既定 cwd より優先する。
- cwd が存在しない、またはアクセス不能な場合は実行前エラーとする。

可搬性要件:

- 実装はパス区切り・絶対/相対解決の差異を吸収し、同一スクリプトの意図が維持されるようにしなければならない。

### 10.6 環境変数規則

実行環境は、プロセス起動時に環境変数集合 `E` を構成する。

構成規則:

1. ベース集合として実行環境既定の変数を取得する。
2. 実装設定または CLI 指定の上書き変数を適用する。
3. セキュリティポリシーで禁止された変数を除外する。

衝突規則:

- 同名キーが複数ソースから与えられた場合、明示指定 > 実装設定 > 環境既定の優先順で解決する。

互換性規則:

- 変数名の大文字小文字感度は実行基盤依存とするが、同一基盤内では一貫した規則で扱わなければならない。

### 10.7 権限境界

各プロファイルは、次の権限境界を明示的に持たなければならない。

- ファイルシステムアクセス境界
- ネットワークアクセス境界
- 実行可能コマンド境界

規則:

- `local` は呼び出しプロセス権限を上限とする。
- `docker` はコンテナ隔離境界内の権限を上限とする。
- `remote` は接続先主体（ユーザー/ロール）の権限を上限とする。
- 権限不足で実行できない場合は実行時エラーとし、原因を診断可能な形で報告しなければならない。

セキュリティ要件:

- 実装は資格情報・秘密値をログへ平文出力してはならない。
- 実装はコマンド実行要求を監査可能な最小情報（環境種別、対象、終了状態）で記録してよい。

### 10.8 環境差異吸収の責務

本仕様における環境差異吸収とは、同一 Lask プログラムの意味を保ったまま異なる実行基盤へ配置可能にする責務を指す。

責務:

- コマンド実行 API（`runCommand`）の戻り値・失敗契約を環境間で統一する。
- 終了コード、stdout、stderr の観測インターフェースを共通化する。
- 環境固有失敗を仕様上の共通エラー分類（14 章）へ写像する。
- 可能な範囲で再試行・接続初期化等の実装差異を内部化し、言語レベル意味論へ漏らさない。

非責務:

- シェル方言差異そのものの完全吸収は要求しない。
- 利用者が指定する外部ツールの意味差異（コマンド自体の挙動差）は本仕様の責務外とする。

記述例:

```lask
showLocal() = $[#local] pwd

showDocker() =
  $[#alpine:3.20] pwd

showRemote() =
  $[#env("ansible")] pwd
```

### 10.9 `remote` の SSH 実行モデル

`remote` 環境は、SSH でサーバへ接続してコマンドを実行する。環境定義ファイル（10.3）のエントリ（`kind: "remote"`）としてのみ構成され、コードからは `#env(name)` で参照する（10.2）。

エントリの `params` の形式（10.2 の `remote` 署名に対応する）:

- `{"host": "..."}`
- `{"host": "...", "user": "..."}`
- `{"host": "...", "user": "...", "port": ...}`

ここで `host` と `user` は文字列、`port` は数値とする。
未指定値は 10.2 の署名の既定値（現在ユーザー、22 番ポート）を用いる。

実行手順:

1. 解決済みの `remote` パラメータ（10.4）を SSH 接続パラメータへ正規化する。
2. ホスト鍵検証ポリシーを適用し、接続可否を判定する。
3. SSH セッションを確立する。
4. 10.5 の cwd 規則と 10.6 の環境変数規則を接続先へ適用する。
5. 指定コマンドを非対話モードで実行する。
6. 終了コード・stdout・stderr を収集し、8.7 の `runCommand` 契約へ写像する。

失敗規則:

- DNS 解決失敗、接続拒否、認証失敗、ホスト鍵不一致、タイムアウトは実行時エラーとする。
- SSH チャネル確立後のコマンド非 0 終了は通常のコマンド失敗として扱う。

セキュリティ規則:

- 実装は既定でホスト鍵検証を有効にしなければならない。
- パスワードや秘密鍵本体をエラーメッセージや監査ログへ出力してはならない。
- 認証情報は実行設定または安全な資格情報ストアから供給し、式値として平文保持しないことが望ましい。

運用規則:

- 実装は必要に応じて SSH 接続再利用（ControlMaster 等）を行ってよい。
- 接続再利用の有無は意味論に影響してはならず、観測可能結果（stdout/stderr/終了コード）は同値でなければならない。

## 11. CLI 仕様

本章では、CLI の外部契約を定義する。

### 11.1 サブコマンド

CLI は次のサブコマンドを提供しなければならない。

- `serve`: エディタ連携（Language Server Protocol）機能を提供する。
- `check`: 静的検証結果を返す。
- `run`: 指定関数を実行する。評価結果は stdout へ出力しない（11.3）。
- `eval`: 指定関数を実行し、評価結果を stdout へ出力する。構文は `run` と同一である（11.2）。
- `infer`: 型推論結果を返す。
- `repl`: 対話的に式・関数を評価できる実行環境を提供する。
- `envs`: タスクが利用する実行環境の列挙と、アクセス可能性の検査を行う（11.4）。

基本呼び出し構文:

```text
lask <subcommand> [options]
```

共通オプション:

- `--module <path>`: 実行対象モジュールを指定する。未指定時は実行ディレクトリの `main.lask` を用いる。
- `--format <text|json>`: CLI 応答の表示形式を指定する。
- `--trace-id <id>`: 実行トレース識別子を指定する。
- `--no-color`: 出力の装飾色を無効化する。

サブコマンド別の最小構文:

```text
lask serve [--stdio | --tcp --port <n>]
lask check [--module <path>]
lask run [--module <path>] <function> [args ...]
lask eval [--module <path>] <function> [args ...]
lask infer [--module <path>] [--symbol <name>]
lask repl [--module <path>]
lask envs [--module <path>] [--env-file <path>] [<function>] [--check]
```

環境指定の方針:

- 実行環境の指定は、言語内の環境式（6.7）でのみ行う。CLI から実行環境を指定・上書きするオプション（`--env` 等）は提供しない。
- これにより、実行環境の指定はすべて静的検証（7.5, 7.7）を通過し、未知の環境種別が実行時の環境解決へ到達することはない（10.4）。
- 実行環境を呼び出しごとに切り替えたい場合は、関数のパラメータ（`String` 等のシリアライズ可能な型）で受けて関数内で環境式を構成する（例: `build(image: String) = $[#docker(image)] ...`）。
- 既定実行環境は常に `#local` である（10.1）。
- 名前付き環境（10.2 の `env`）の定義は、`--env-file <path>` で指定した環境定義ファイル（10.3）から読み込む。未指定時はモジュール解決の基準ディレクトリの `environments.lask.json` を用いる。差し替えはファイル単位の全置換とし、複数ファイルのマージは行わない。

SSH 実行設定オプション:

- `--ssh-known-hosts <path>`: 既知ホストファイルを指定する。
- `--ssh-strict-host-key-checking <yes|accept-new|no>`: ホスト鍵検証方針を指定する。
- `--ssh-connect-timeout <sec>`: SSH 接続タイムアウトを秒で指定する。

規則:

- `--ssh-*` オプションは接続設定であり、実行中に `remote` 環境の解決（10.9）が行われる場合、および `envs --check`（11.4）の接続検査に適用される。
- `remote` 環境が一度も解決されない場合、`--ssh-*` の指定は無視してよいが、エラーとしてはならない。
- 接続設定は `Environment` 値の一部ではなく、10.9 にいう「実行設定」として扱う。式値・実行イベントへ含めてはならない。

### 11.2 関数呼び出し

- CLI は関数を直接呼び出す。呼び出す関数は `run` / `eval` の第 1 位置引数として指定する（`--function` オプションは提供しない）。
- 関数の引数は、位置引数と、一般的な CLI 規約に沿ったオプション形式のキーワード引数で与える。
- 引数の解釈・デコード方式を指定できる。

関数呼び出し構文:

```text
lask run  [--module <path>] [--arg-decode <mode>] [lask オプション ...] <function> [args ...]
lask eval [--module <path>] [--arg-decode <mode>] [lask オプション ...] <function> [args ...]
```

- `run` と `eval` の呼び出し構文は同一とする。本節の規則（関数名の写像、キーワード引数、束縛、デコード）は両者へ等しく適用される。
- `--module` 未指定時は `main.lask` を対象とする。したがって最小形は `lask run <function> [args ...]` / `lask eval <function> [args ...]` となる。
- `lask` 自身のオプション（`--module`、`--arg-decode`、`--ssh-*`、`--format` 等）は関数名より前に置かなければならない。**関数名より後のトークンは、すべて関数への引数として解釈する**（`lask` オプションと関数キーワード引数の衝突を防ぐ境界規則）。

関数名・パラメータ名の写像規則:

- 関数名およびキーワード引数名に含まれる `-` は、名前解決の前にすべて `_` へ置換する（kebab-case 呼び出しの許容）。例: `lask run show-version` はトップレベル関数 `show_version` を解決し、`--out-dir dist` はパラメータ `out_dir` へ束縛する。
- 置換後の名前で照合し、該当がない場合は未定義参照エラーとする。
- 識別子に `-` は含められない（3.2）ため、この写像によって複数の候補が同名へ写ることはなく、解決は常に一意である。
- camelCase の名前（`buildAndTest` 等）は写像の対象外であり、そのままの名前で指定する。

キーワード引数の形式:

- パラメータ `p` に対するキーワード引数は `--p <value>` または `--p=<value>` で与える。
- パラメータ名が 1 文字の場合は、短形式 `-p <value>` も使用できる。
- 例: `retry(cmd: String, --n: Number = 3)` に対する `lask run retry "make test" -n 5` は、関数呼び出し `retry("make test", n = 5)` に相当する。

束縛規則:

1. 対象モジュール（`--module`、既定 `main.lask`）を解決し、第 1 位置引数で指定されたトップレベル関数を取得する。
2. 関数名より後の位置引数を左から順に、宣言順の位置パラメータへ束縛する。位置パラメータ数を超える位置引数は、可変長パラメータへ収集する（7.5 の可変長収集）。
3. キーワード引数を、名前が一致するパラメータへ束縛する。未知の名前・重複束縛は実行前エラーとする（7.5 の `E-TYPE-KEYWORD` に対応）。
4. 束縛されなかったキーワードパラメータは、関数定義の既定値で補完する（7.5 の既定値補完）。
5. 位置引数の個数が位置パラメータ数と一致しない場合（可変長パラメータによる収集を除く）は実行前エラーとする。

引数デコード方式:

- `--arg-decode text`: すべての引数を `String` として扱う。
- `--arg-decode json`: 各引数を JSON 値として解釈する。
- `--arg-decode auto`: JSON として解釈可能なら JSON、不能なら `String` とする。
- 未指定時の既定値は `auto` とする。
- デコードは位置引数・キーワード引数の値の両方へ適用する。

型整合規則:

- 束縛後の各引数は 7.5 の呼び出し整合性を満たさなければならない。
- `auto` モードで曖昧な場合は `String` を優先する。
- デコード失敗または型不一致は関数評価開始前にエラーとして報告しなければならない。
- `Environment` 型の位置パラメータを持つ関数は、CLI 直接起動の対象外とする（いずれのデコード方式でも `Environment` 値を構成できないため、実行前エラーとする）。`Environment` 型のキーワードパラメータは既定値で補完されるが、CLI から値を与えることはできない。環境を外部から選択する場合は、`String` 等で受けて関数内で環境式を構成する。

`run` と `eval` の差異:

- `run` と `eval` の差異は評価結果の扱いのみとする。`eval` は評価結果を stdout へ出力し、`run` は出力しない（11.3）。
- 束縛・評価・失敗の伝播・終了コードの意味論は両者で同一である。
- `eval` は、返却値をシェルパイプで他のコマンドや別の `lask` 呼び出しへ渡し、タスクを即席で結合する用途を想定する。単発のタスク実行では返却値の出力がノイズになるため、通常は `run` を用いる。

### 11.3 入出力契約

CLI の入出力は 9 章の契約に従い、次を満たさなければならない。

標準入力契約:

- stdin は常に UTF-8 文字列として読み取り、`String` 値として `stdin` へ束縛する（9.2〜9.4）。デコード方式を選択するオプション（`--stdin-decode` 等）は提供しない。
- 行分割・JSON 解釈などの構造化は、関数内で `split` / `fromJson` 等を適用して行う。
- `run` / `eval` は stdin を受け付ける。
- `repl` は stdin を対話入力に用いるため、`stdin` 参照変数を提供しない（9.2, 9.3）。
- `check` / `infer` / `serve` は stdin を受け付けてもよいが、意味はサブコマンド仕様で定義しなければならない。

標準出力契約:

- `--stdout-encode <text|json|pretty-json>` を指定できる。
- 未指定時の既定値は `json` とする。
- `text` は人間可読表示、`json` は機械可読表示、`pretty-json` は整形 JSON 表示とする。
- `eval` は評価結果を指定エンコード方式で stdout へ出力する。
- `run` は評価結果を stdout へ出力しない。`run` は stdout へ何も出力してはならない。
- `check` と `infer` は診断結果を stdout へ出力する。
- `run` / `eval` とも、実行ログ・診断の出力先は stderr である（9.6, 12 章）。

標準エラー契約:

- stderr はログの出力先である（9.6）。`run` / `eval` の実行中は、コマンド実行ログ（12.3）が stderr へリアルタイムに出力される。
- 実行失敗時は stderr にエラーコード、要約、必要に応じて位置情報を出力する。
- `--format json` 指定時、stderr の出力は JSON Lines を正準形とする（12.2）。
- 秘密情報は stderr に平文出力してはならない。

終了コード契約:

- `0`: 成功
- 未捕捉の失敗: `Error` 値の `code`（8.10）。コマンド失敗はそのコマンドの終了コードを、その他の実行時エラーは既定 `2`、外部 I/O エラー（SSH 接続失敗、環境解決失敗を含む）は既定 `3`、`fail` は指定値を透過する。`code` が 1〜255 の整数でない場合は `1` へ正規化する。
- `1`: 構文・静的検証エラー（評価前に検出され、`Error` 値は生成されない）
- `4`: CLI 使用エラー（不正オプション、不足引数など）

終了コードの重なり:

- コマンドが終了コード `1` や `4` で失敗した場合、プロセス終了コードのみでは構文エラー・CLI 使用エラーと判別できない。終了コードは復旧・スクリプト連携のための一次情報とし、種別の正確な判別は stderr の機械可読診断（エラーコード。14 章）で行う。

代表例:

```text
# 型検査のみ（main.lask が既定対象）
lask check

# 関数実行（ローカル。main.lask 内で fromJson(stdin) により JSON を解釈）
echo '{"name":"alice"}' | lask run greet

# キーワード引数付き実行（main.lask 内: greet(name: String, --prefix: String = "hello")）
lask run greet alice --prefix hi

# 可変長引数（main.lask 内: sum(...xs: Array<Number>)）
lask run sum 1 2 3

# 固定イメージ上で実行（ci.lask 内: build() = $[#alpine:3.20] ...）
lask run --module ci.lask build

# リモート環境での実行（ops.lask 内: provision() = $[#env("ansible")] ...。環境定義は environments.lask.json）
lask run --module ops.lask \
  --ssh-known-hosts ~/.ssh/known_hosts \
  --ssh-strict-host-key-checking yes \
  --ssh-connect-timeout 10 \
  provision

# 利用環境の列挙とアクセス検査
lask envs provision --check
```

### 11.4 環境確認（`envs`）

`envs` は、タスクが利用する実行環境の列挙と、アクセス可能性の検査を行う。

構文:

```text
lask envs [--module <path>] [--env-file <path>] [<function>] [--check]
```

列挙規則:

- 関数の指定がない場合、モジュール全体が参照する環境を列挙する（環境式の静的走査と、環境定義ファイル（10.3）の定義の突き合わせ）。
- `<function>` を指定した場合、その関数から到達可能な呼び出しグラフ上で使用される環境に限定する。関数名の写像は 11.2 に従う。
- 到達可能性は過大近似とする。使用しうる環境の上位集合を報告しなければならず、過小報告してはならない。関数値として受け渡される関数は保守的に含める。
- `#docker(image)` の `image` が実行時値の場合は、動的イメージの `docker` 環境として列挙する。`#env` は名前が静的に確定する（10.2）ため、常に具体的に列挙される。

検査規則（`--check`）:

- 列挙された各環境について、コマンドを一切実行せずに到達性のみを検査する。検査は対象環境に対して副作用を持ってはならない。
- `local`: 常に成功とする。既定 cwd（10.5）の存在検査を含めてよい。
- `docker`: Docker デーモンへの接続可否を検査する。イメージ参照の解決（ローカル存在・レジストリ照会）は実装定義の深さとし、イメージの取得（pull）は行わない。
- `remote`: SSH 接続の確立（ホスト鍵検証・認証を含む）までを検査する。10.9 のセキュリティ規則を適用し、`--ssh-*` オプション（11.1）を使用できる。
- 1 つの環境の検査失敗で中断せず、すべての環境を検査してまとめて報告する。

出力と終了コード:

- 環境ごとに、参照名（名前付き環境の場合）、環境種別、対象の要約、検査結果（`--check` 時）を出力する。`--format json` で構造化出力できる。
- 検査に失敗した環境には、エラーコード（`E-IO-SSH-CONNECT`、`E-IO-ENV-RESOLVE` 等。14 章）と要約を含める。
- 終了コード: 列挙・検査がすべて成功した場合は `0`、アクセス不能な環境が 1 つ以上ある場合は `3`、静的エラー（未定義の環境名、環境定義ファイルの不正等）は `1`、CLI 使用エラー（存在しない関数名等）は `4` とする（11.3 の分類に従う）。

実行例:

```text
$ lask envs provision --check
ansible  remote  automation@203.0.113.10:22  ok
builder  docker  golang:1.22                 ok
```

## 12. 観測性

本章では、実行の観測手段を定義する。

### 12.1 観測対象と設計原則

観測性は、実行の理解・障害解析・運用監査のために必要な情報を一貫形式で提供する要件である。

実装は少なくとも次を観測対象として扱わなければならない。

- 関数呼び出し境界（開始・終了・失敗）
- 環境実行境界（`#local` / `#docker(...)` / `#env(...)`）
- 外部コマンド実行（開始・終了コード・出力要約）
- 型検証・実行時診断

設計原則:

- 低侵襲: 観測の有無で言語意味論（7, 8 章）を変えてはならない。
- 相関可能: 同一実行に属するログ・イベントを追跡できなければならない。
- 機械可読: 少なくとも 1 つの構造化形式（JSON 等）を提供しなければならない。
- 秘密保護: 機密情報を既定で露出してはならない。

### 12.2 実行ログ

実行ログは時系列の診断情報であり、少なくとも次のフィールドを含まなければならない。

- `timestamp`: 時刻（UTC 推奨）
- `level`: `debug` / `info` / `warn` / `error`
- `traceId`: 12.5 で定義する識別子
- `message`: 人間可読メッセージ
- `context`: 任意の補助情報（関数名、モジュール名、環境種別等）

出力規則:

- `info` 以下は運用ログ、`warn` / `error` は診断ログとして分類する。
- `error` レベルログは、対応する失敗イベント（12.6）と相互参照可能でなければならない。
- 既定のテキスト表示の行形式は実装定義とする。ただし各行に `level`・`message` を含み、コマンド実行ログ（12.3）はテキスト形式の規定に従う。
- `--format json` 指定時、stderr に出力するログ・コマンド実行ログ・エラー診断・実行イベントは、JSON Lines（1 行 1 オブジェクト）で出力しなければならない（正準形）。行の種別は、フィールドの有無（`kind` = 実行イベント（13.3）、`code` + `stage` = エラー診断（14.3）、`stream` / `event` = コマンド実行ログ（12.3））で判別できる。

### 12.3 コマンド実行ログ

`runCommand`（8.7）の実行中、実装は子プロセスの標準出力・標準エラーを、コマンド実行ログとして自身の stderr へリアルタイムに中継しなければならない。中継は `CommandResult` への取り込み（8.7）と並行して行い、評価結果（値の意味論）に影響してはならない。

中継規則:

- 中継は行単位で逐次行う（行バッファリング）。子プロセスの終了までまとめて出力してはならない。
- 対象は `run`・`eval` の実行、および `envs --check`（11.4）の接続診断とする。`$`・`$1`・`$2`・`$*` のいずれの糖衣で実行されたかによらず、中継の内容は同一とする。
- コマンド実行ごとに、トップレベル実行内で一意な 1 始まりの連番（実行番号）を割り当てる。並行実行（`async`）でも実行番号は重複しない。
- 各ログ行はタイムスタンプと実行番号付きの環境要約を含む。実行コマンドは開始行にのみ記載し、以降の行は実行番号で対応付ける（全行へのコマンド記載は行わない）。
- 12.8 の秘密情報マスクを中継内容へ適用する。出力量の上限・抑制手段（レート制限、抑制オプション等）は実装定義として提供してよい。

テキスト形式（既定）:

各行を次の構成で出力する。

```text
<timestamp> [<環境要約>:<実行番号>] <種別> <内容>
```

- `timestamp`: UTC の ISO 8601 形式。
- 環境要約: 環境式（6.7）の表記に準じる。`#local`、`#<イメージ>`（docker）、`#env(<名前>)`（名前付き環境）。
- 実行番号: 中継規則で割り当てた連番。
- 種別: `$`（開始行。内容として実行コマンド文字列を記載する）、`1|`（子プロセスの標準出力）、`2|`（子プロセスの標準エラー）、`exit <code>`（終了。終了コード付き）。`1`・`2` はファイルディスクリプタ番号（6.6 のストリーム指定子と同じ体系）である。
- 開始行（`$`）と `exit` 行は、コマンド実行ごとに必ず発行する。開始行のコマンド文字列は実装定義の長さで切り詰めてよい。

出力例:

```text
2026-07-23T10:15:04.123Z [#golang:1.22:1] $ go build ./...
2026-07-23T10:15:04.320Z [#golang:1.22:1] 1| compiling module...
2026-07-23T10:15:04.751Z [#golang:1.22:1] 2| warning: unused variable
2026-07-23T10:15:05.002Z [#golang:1.22:1] exit 0
```

JSON 形式（`--format json` 時）:

- コマンド実行ログの各行を、12.2 の JSON Lines の 1 オブジェクトとして出力する。
- 全行の必須フィールド: `timestamp`、`level`、`traceId`、`exec`（実行番号）。
- 開始行: `event: "start"` に加え、`command`（実行コマンド文字列）と `env`（13.1 のメタデータ表現。名前付き環境は `name` を含む）を必須とする。
- 中継行: `stream`（`1` または `2`）と `message`（行の内容）を必須とする。`command`・`env` は省略してよい（`exec` で開始行と対応付ける）。
- 終了行: `event: "exit"` と `code`（終了コード）を必須とする。

レベル規則:

- 中継行（`1|`・`2|`）と開始行（`$`）は `info` とする。
- `exit` は終了コード `0` のとき `info`、非 0 のとき `warn` とする。

### 12.4 スタックトレース

実装は、実行失敗時にスタックトレースを常時生成・記録できなければならない。生成するスタックトレースは次を満たさなければならない。

- 少なくとも関数名、呼び出し順序、可能であればソース位置（行・列またはスパン）を含む。
- 非同期境界（`spawn` / `await`）をまたぐ場合、親子関係が追跡可能であること。
- コマンド実行（`runCommand`）を含む失敗では、環境種別と実行コマンド要約を含めてよい。

省略規則:

- ユーザー向け表示では内部ランタイムフレームを省略してよい。
- ただし省略しても、障害原因特定に必要なフレームは残さなければならない。

### 12.5 トレース識別子

トレース識別子 `traceId` は同一実行単位の観測情報を関連付けるための識別子である。

生成・伝播規則:

- CLI の `--trace-id` 指定時はその値を採用する。
- 未指定時は実装が衝突しにくい識別子を自動生成する。
- 同一トップレベル実行に属するログ・イベント・エラーは同一 `traceId` を共有する。
- `remote` 環境での実行時は、必要に応じて接続先へ `traceId` を伝播してよい。

整合規則:

- 1 つの `traceId` に対して複数のトップレベル実行を混在させてはならない。

### 12.6 実行イベント出力

実行イベントは 13.3 の `ExecutionEvent` 形式で表現する。

イベント発行規則:

- 関数呼び出し開始時に `CallEvent` を発行する。
- 正常終了時に `ReturnEvent` を発行する。
- 失敗終了時に `FailEvent` を発行する。

最小保証:

- 1 つの `CallEvent` には、最終的に `ReturnEvent` または `FailEvent` のいずれか 1 つが対応しなければならない。
- イベント順序は同一関数実行について因果順序を保存しなければならない。
- コマンド実行（`runCommand`）を伴う場合、`ArgumentsSummary` に環境種別要約を含めてよい。
- 失敗が `try` / `catch`（6.9）で捕捉された場合も、失敗した関数呼び出しに対応する `FailEvent` は発行する。捕捉によってイベントを取り消してはならない。

### 12.7 実行中診断情報

実装は、長時間実行や対話モードで進捗診断を提供してよい。

対象:

- `serve`: 解析開始/完了、エラー件数、再解析トリガー
- `repl`: 評価開始/終了、直近エラー要約
- `run` / `eval`: 実行段階（解決、型検証、評価、外部コマンド実行）

規則:

- 実行中診断は主結果（`eval` の stdout 出力）を破壊してはならない。
- 人間向け進捗表示は stderr または専用チャネルへ出力しなければならない。
- `--format json` 指定時、進捗診断を構造化イベントとして出力してよい。

### 12.8 機密情報保護と保持方針

観測データには機密情報が混入し得るため、実装は以下を満たさなければならない。

- 環境変数値、資格情報、秘密鍵、トークンはマスクまたは除去する。
- コマンド引数は必要に応じて要約化し、全文出力を避ける。
- SSH 認証失敗時も秘密情報そのものを出力してはならない。

保持方針:

- 既定の保持期間・サイズ上限を実装が定めること。
- ローテーション時はイベント整合（12.6）を壊さないこと。
- 監査要件がある場合、改ざん検知可能な保存形式を採用してよい。

## 13. シリアル化規約

本章では、データ値・関数値・イベントの外部表現規約を定義する。

### 13.1 データ値

本節は、データ値の正準シリアル化形式を定義する。

形式プロファイル:

- `json`: 機械可読な正準 JSON 形式
- `pretty-json`: `json` と同一情報を整形出力した形式
- `text`: 人間可読形式（実装定義）。ただし情報欠落を起こしてはならない

`json` / `pretty-json` では、次の写像規則を満たさなければならない。

- `Number`: JSON number へ写像する。
- `String`: JSON string へ写像する。
- `Bool`: JSON boolean へ写像する。
- `Null`: JSON null へ写像する。
- `Void`: 直接シリアライズ対象外（4.5）。出力が必要な場合は、タグ付きメタデータ `{"$type":"Void"}` へ変換する（13.2 の `FunctionRef` と同等の扱い）。
- `Environment`: 直接シリアライズ対象外（4.5）。出力が必要な場合は、タグ付きメタデータ `{"$type":"Environment","kind":"<環境種別>","params":{...}}` へ変換する。`kind` は環境種別名、`params` は正規化済みパラメータ集合とする（例: `{"$type":"Environment","kind":"docker","params":{"image":"alpine:3.20"}}`）。秘密情報を含むパラメータは 12 章の規則に従いマスクする。
- `Array<T>`: 要素順を保持した JSON array へ写像する。
- `Map<T>`: キーが文字列の JSON object へ写像する。
- `Record<...>`: フィールド名をキーとする JSON object へ写像する。

`Any` の規則:

- `Any` は実体値のシリアル化規則に従って写像する。
- 実体値が `Void` または `Environment` の場合はタグ付きメタデータ表現へ変換し、実体値が関数値の場合は `FunctionRef`（13.2）へ変換する。

タグ付きメタデータの往復規則:

- `fromJson` / `decode`（15.8）は `$type` フィールドを特別扱いせず、タグ付きメタデータを通常のオブジェクト（`Record` または `Map`）として読み込む。
- したがって `Void`・`Environment`・関数値のシリアライズ結果からの復元（往復変換）は保証されない。

数値規則:

- `NaN`, `+Infinity`, `-Infinity` は JSON 正準形式に直接表現できないため、既定ではシリアル化エラーとする。
- 実装が拡張表現を提供する場合、CLI オプションで明示有効化しなければならない。

キーと順序の規則:

- `Record<...>` は定義順で出力してよい。
- `Map<T>` は順序を保証しない。
- 同一キーの重複は許可しない。

文字エンコード:

- 文字列は UTF-8 で入出力しなければならない。
- 制御文字や引用符は JSON 規則に従ってエスケープしなければならない。

### 13.2 関数値

`Function<T1, T2, ..., R>` は直接シリアル化対象外とする。

規則:

- 関数本体（コード）やクロージャ環境をそのまま外部化してはならない。
- 関数値を外部出力する必要がある場合は、参照メタデータ `FunctionRef` へ変換しなければならない。

`FunctionRef` の最小フィールド:

- `$type`: 固定値 `"FunctionRef"`
- `module`: 定義モジュール識別子
- `name`: 関数名
- `arity`: 位置パラメータ数（7.5 の `m`）
- `variadic`: 可変長パラメータ（6.1）を持つ場合は `true` を設定する。持たない場合は省略してよい。
- `type`: 関数型の文字列表現（例: `Function<String, Number>`）

例:

```json
{
  "$type": "FunctionRef",
  "module": "app/main.lask",
  "name": "greet",
  "arity": 1,
  "type": "Function<String, String>"
}
```

匿名関数・クロージャ規則:

- 安定参照名を持たない関数値は、`name` を実装生成識別子（例: `<lambda@L10C5>`）としてよい。
- 閉包された自由変数の実体値は、既定で `FunctionRef` に含めてはならない。

### 13.3 実行イベント

```ebnf
ExecutionEvent = CallEvent | ReturnEvent | FailEvent .
CallEvent      = "call" EventCommon .
ReturnEvent    = "return" EventCommon .
FailEvent      = "fail" EventCommon ErrorInfo .
EventCommon    = TraceId FunctionRef ArgumentsSummary ResultSummary Timestamp .
```

実行イベントは 12.6 の発行規則に従い、`json` または `pretty-json` で次のフィールドを含まなければならない。

- `kind`: `call` / `return` / `fail`
- `traceId`: 同一実行相関 ID
- `timestamp`: イベント時刻
- `function`: `FunctionRef`
- `args`: 引数要約（`call` で必須）
- `result`: 戻り値要約（`return` で必須）
- `error`: エラー情報（`fail` で必須）
- `env`: 実行環境要約（環境種別 `kind` と正規化済みパラメータ要約 `params`。名前付き環境（10.3）の場合は参照名を `name` として含めてよい）

`ErrorInfo` の最小フィールド:

- `code`: エラーコード（14 章）
- `message`: 人間可読要約
- `detail`: 任意詳細（安全に開示可能な範囲）

因果整合規則:

- 同一関数実行について `call` の後に `return` または `fail` が 1 回だけ対応しなければならない。
- `timestamp` は同一トレース内で非減少順序を保つことが望ましい。
- 非同期実行の子イベントは同一 `traceId` を共有し、必要に応じて親子関係 ID を付与してよい。

実行イベントは少なくとも以下を保持する。

- 追跡可能な識別子
- 対象関数
- 引数要約
- 戻り値要約
- 失敗時エラー情報

例:

```json
{
  "kind": "fail",
  "traceId": "trc-01J8Y2...",
  "timestamp": "2026-07-11T12:34:56Z",
  "function": {
    "$type": "FunctionRef",
    "module": "ops/deploy.lask",
    "name": "deploy",
    "arity": 1,
    "type": "Function<String, String>"
  },
  "args": {"summary": ["prod"]},
  "env": {"kind": "remote", "params": {"host": "prod.example.com", "user": "deployer", "port": 22}},
  "error": {
    "code": "E-IO-SSH-CONNECT",
    "message": "ssh connection timeout",
    "detail": {"timeoutSec": 10}
  }
}
```

## 14. エラー体系

本章では、エラー分類と診断情報の最小要件を定義する。

### 14.1 エラー分類

本仕様のエラーは、発生段階により次の 4 区分へ分類する。

- 構文エラー: 字句解析・構文解析で検出される不正
- 静的エラー: 名前解決・型検証・モジュール解決で検出される不正
- 実行時エラー: 評価中に発生する不正（ゼロ除算、コマンド非 0 終了など）
- 外部 I/O エラー: ファイル・ネットワーク・SSH・環境解決など外部境界での失敗

分類規則:

- 1 件のエラーは主分類を 1 つだけ持たなければならない。
- 複合要因がある場合、最初に観測された根本原因分類を採用する。

### 14.2 エラーコード規約

エラーコードは `E-<CATEGORY>-<DETAIL>` 形式とする。

カテゴリ一覧:

- `SYNTAX`: 構文エラー
- `NAME`: 名前解決エラー
- `TYPE`: 型検証エラー
- `MODULE`: モジュール解決エラー
- `RUNTIME`: 評価中エラー
- `IO`: 外部 I/O エラー
- `CLI`: CLI 使用エラー

命名規則:

- 英大文字とハイフンのみを用いる。

代表コード:

- `E-SYNTAX-UNEXPECTED-TOKEN`
- `E-SYNTAX-RETURN-POSITION`
- `E-NAME-UNDEFINED`
- `E-NAME-AMBIGUOUS`
- `E-NAME-DUPLICATE`
- `E-TYPE-MISMATCH`
- `E-TYPE-ARITY`
- `E-TYPE-CALL`
- `E-TYPE-COMMAND-ENV`
- `E-TYPE-ENV-CONSTRUCT`
- `E-TYPE-ACCESS`
- `E-TYPE-FIELD-DUPLICATE`
- `E-TYPE-KEYWORD`
- `E-TYPE-ILLFORMED`
- `E-MODULE-CYCLE`
- `E-RUNTIME-DIV-BY-ZERO`
- `E-RUNTIME-COMMAND-NONZERO`
- `E-RUNTIME-AWAIT-FAILED`
- `E-RUNTIME-ACCESS`
- `E-RUNTIME-CAST`
- `E-IO-STDIN-READ`
- `E-IO-SSH-CONNECT`
- `E-IO-ENV-RESOLVE`
- `E-IO-DATA-DECODE`
- `E-CLI-USAGE`

### 14.3 診断情報の最小要件

実装は、エラー報告時に少なくとも次を含めなければならない。

- `code`: エラーコード
- `message`: 人間可読メッセージ
- `stage`: `syntax` / `static` / `runtime` / `io` / `cli`
- `traceId`: 利用可能な場合は 12.5 の識別子
- `location`: 可能であれば行・列またはスパン

型・名前関連の追加要件:

- 型不一致では `expected` と `actual` を含める。
- 名前解決失敗では候補または探索範囲要約を含めてよい。

JSON 形式例:

```json
{
  "code": "E-TYPE-MISMATCH",
  "message": "argument type mismatch",
  "stage": "static",
  "traceId": "trc-01J8Y2...",
  "location": {"line": 12, "column": 8},
  "expected": "Number",
  "actual": "String"
}
```

### 14.4 静的エラー

静的エラーは、実行前検証（7 章）で報告される。

最小対象:

- `E-NAME-UNDEFINED`
- `E-NAME-AMBIGUOUS`
- `E-NAME-DUPLICATE`
- `E-TYPE-MISMATCH`
- `E-TYPE-ARITY`
- `E-TYPE-CALL`
- `E-TYPE-COMMAND-ENV`
- `E-TYPE-ENV-CONSTRUCT`
- `E-TYPE-ACCESS`
- `E-TYPE-FIELD-DUPLICATE`
- `E-TYPE-KEYWORD`
- `E-TYPE-ILLFORMED`
- `E-MODULE-CYCLE`

規則:

- 静的エラーが 1 件以上ある場合、`run` / `eval` の評価を開始してはならない。
- 複数エラー検出時は、可能な限り継続解析してまとめて報告してよい。

### 14.5 実行時エラー

実行時エラーは、動的意味論（8 章）の評価中に発生する。

代表例:

- `E-RUNTIME-DIV-BY-ZERO`: 算術不正
- `E-RUNTIME-COMMAND-NONZERO`: コマンド実行式（`$`・`$1`・`$2`。6.6）の非 0 終了に起因する失敗
- `E-RUNTIME-AWAIT-FAILED`: `await` が失敗状態を再送出
- `E-RUNTIME-ACCESS`: 添字範囲外・キー不在（8.9）
- `E-RUNTIME-CAST`: `cast` の実行時型検査の失敗（15.8）

規則:

- 実行時エラーは発生地点から外側式へ伝播する（8.10）。
- 失敗時は 12 章の観測規則に従って `FailEvent` を発行しなければならない。

### 14.6 外部 I/O エラー

外部 I/O エラーは、言語外部境界で発生する。

代表例:

- `E-IO-STDIN-READ`: stdin 読み取り失敗
- `E-IO-ENV-RESOLVE`: 実行環境解決失敗
- `E-IO-SSH-CONNECT`: SSH 接続失敗
- `E-IO-SSH-AUTH`: SSH 認証失敗
- `E-IO-FS`: ファイルシステムアクセス失敗
- `E-IO-DATA-DECODE`: 入力データのデコード失敗（9.4 の stdin デコード、15.8 の `fromJson`/`decode`）

規則:

- 外部 I/O エラーは、可能な範囲で再試行可能性を付与して報告してよい。
- 機密情報（鍵、トークン、パスワード）は `detail` に含めてはならない。

### 14.7 復旧可能性と伝播規則

復旧可能性:

- `recoverable`: 再試行・入力修正・設定変更で復旧可能
- `non-recoverable`: プロセス継続が妥当でない失敗

既定分類:

- 構文・静的エラーは `recoverable`（ソース修正前提）
- 実行時エラーは実装定義だが、既定では `non-recoverable`
- 外部 I/O エラーは原因に応じて `recoverable` または `non-recoverable`

伝播規則:

- `do` / コレクション関数（`map`・`filter`・`reduce`・`forEach`） / `await` を含む式では 8.10 の失敗伝播規則に従う。
- `try` / `catch`（6.9）で明示的に捕捉されない限り、失敗はトップレベルまで伝播し、プロセスは `Error` 値の `code` で終了する（8.10, 11.3）。
- `recoverable` / `non-recoverable` の分類は診断・運用のための情報であり、捕捉可否には影響しない。評価中の実行時エラー・外部 I/O エラーはいずれも捕捉できる。

### 14.8 CLI 終了コードとの対応

CLI は 11.3 の終了コード契約に従い、エラー分類を次へ写像する。

- 構文・静的エラー -> `1`
- 実行時エラー -> 未捕捉の `Error` 値の `code`（既定 `2`。コマンド失敗は子プロセスの終了コードを透過する。8.10）
- 外部 I/O エラー -> 未捕捉の `Error` 値の `code`（既定 `3`）
- CLI 使用エラー -> `4`

規則:

- 同時に複数分類が存在する場合は、最初に発生した致命分類の終了コードを採用する。
- `--format json` 時、終了コードに対応するエラーオブジェクトを stderr に出力しなければならない。
- 終了コードの正規化（1〜255 外の値は `1`）と終了コードの重なりの扱いは 11.3 に従う。

## 15. 組み込みライブラリ

本章では、言語処理系がデフォルトで提供する関数・演算子・環境操作を定義する。

### 15.1 提供方針

組み込みライブラリは、明示 import なしで利用可能な組み込みシンボル集合とする。

方針:

- 参照透過な純関数を優先する。
- 外部副作用を伴う関数は、名称と契約で明確に区別する。

公開規則:

- 組み込みライブラリのシンボルは名前解決の最下位（7.2 の第 5 順位）に位置する。ユーザー定義で同名シンボルを宣言した場合、通常の名前解決規則に従ってシャドーイングしてよい。
- ただし 6 章で「上書き禁止」と規定したコア関数名は宣言・束縛できない（7.2）。

型付け規則:

- 本章の署名に現れる型変数（`T`、`U` 等）は、4.4 の組み込み多相規則に従う。多相型を持てるのは組み込みシンボルのみであり、ユーザー定義関数の署名には型変数を使用できない。

### 15.2 数値演算

組み込みライブラリとして、少なくとも次の関数を提供する。

- `add`: `Function<Number, Number, Number>`
- `sub`: `Function<Number, Number, Number>`
- `mul`: `Function<Number, Number, Number>`
- `div`: `Function<Number, Number, Number>`
- `mod`: `Function<Number, Number, Number>`
- `abs`: `Function<Number, Number>`
- `floor`: `Function<Number, Number>`
- `ceil`: `Function<Number, Number>`
- `round`: `Function<Number, Number>`

意味論:

- `add`/`sub`/`mul`/`div`/`mod` は 6.2 の算術演算子と同値の意味を持つ。
- `div` の除数が 0 の場合は `E-RUNTIME-DIV-BY-ZERO` とする。
- `mod` の右辺が 0 の場合も `E-RUNTIME-DIV-BY-ZERO` とする。

### 15.3 文字列操作

組み込みライブラリとして、少なくとも次の関数を提供する。

- `length`: `Function<String, Number>`
- `concat`: `Function<String, String, String>`
- `trim`: `Function<String, String>`
- `toLower`: `Function<String, String>`
- `toUpper`: `Function<String, String>`
- `split`: `Function<String, String, Array<String>>`
- `join`: `Function<Array<String>, String, String>`
- `replace`: `Function<String, String, String, String>`

意味論:

- 文字列は UTF-8 として扱う。
- `length` は文字数単位で計数してよいが、実装は計数規則を一貫させなければならない。
- `split`/`join` は区切り文字列が空文字の場合の挙動を実装定義としてよい。
- `concat` は 2 つの文字列を連結する。3 つ以上を連結する場合は `concat` の入れ子適用または `join` を用いる。
- 文字列連結は `concat`（または `join`）で行う。`+` は `Number` 専用であり、`String` へ適用した場合は型エラーとする（6.2）。

### 15.4 配列・マップ・レコード操作

組み込みライブラリとして、少なくとも次の関数を提供する。

- `map`: `Function<Array<T>, Function<T, U>, Array<U>>`
- `filter`: `Function<Array<T>, Function<T, Bool>, Array<T>>`
- `reduce`: `Function<Array<T>, U, Function<U, T, U>, U>`
- `forEach`: `Function<Array<T>, Function<T, U>, Void>`
- `append`: `Function<Array<T>, T, Array<T>>`
- `concatArray`: `Function<Array<T>, Array<T>, Array<T>>`
- `get`: `Function<Map<T>, String, T>`
- `hasKey`: `Function<Map<T>, String, Bool>`
- `keys`: `Function<Map<T>, Array<String>>`
- `values`: `Function<Map<T>, Array<T>>`

意味論:

- `map`/`filter`/`reduce`/`forEach` は入力配列を左から右へ走査する（評価規則は 8.5）。
- `reduce` は初期値を必須とする。
- `forEach` は各適用結果を捨てて `Void` を返す。副作用目的の反復に用いる。
- `map`、`filter`、`reduce`、`forEach` は 6.4 の制御構造の正規化先を含むコア関数であり、ユーザーコードから上書きしてはならない（15.1 の例外規定に従う）。
- `get` はキー不在時に実行時エラー（`E-RUNTIME-ACCESS`）とする。添字アクセス `m[k]`（6.8, 8.9）と同一の失敗契約である。キー不在を許容する場合は `hasKey` で事前に検査する。

### 15.5 コマンド実行関数

組み込みライブラリとして、少なくとも次の関数を提供する。

- `runCommand`: `Function<String, CommandResult>`（キーワードパラメータ `--env: Environment = #local` を持つ）

契約:

- 6.6, 8.7, 10 章の規則に従う。`CommandResult` は 6.6 で定義される組み込み型エイリアスである。
- `runCommand` は、コマンドが完了すれば終了コードに関わらず成功する。コマンド実行式 `$`・`$1`・`$2`（6.6）の非 0 終了に起因する失敗の診断コードは `E-RUNTIME-COMMAND-NONZERO` とする。
- 環境解決失敗は `E-IO-ENV-RESOLVE` とする。

### 15.6 並列・非同期補助関数

組み込みライブラリとして、少なくとも次の関数を提供する。

- `spawn`: `Function<Function<T>, AsyncHandle<T>>`
- `await`: `Function<AsyncHandle<T>, T>`
- `all`: `Function<Array<AsyncHandle<T>>, Array<T>>`
- `race`: `Function<Array<AsyncHandle<T>>, T>`

意味論:

- `spawn`/`await` は 6.3, 8.6 の規則に従う。
- `await` は予約語であるため `AwaitExpr` の形（`await h`）でのみ適用でき、関数値として渡す場合は `\(h) -> await h` と記述する（6.3）。
- `all` は全ハンドルの完了を待ち、入力順に結果配列を返す。
- `race` は最初に成功または失敗した結果を返す。

失敗規則:

- `all` はいずれか 1 つが失敗した時点で失敗としてよい。
- `await` で失敗結果を受け取る場合は `E-RUNTIME-AWAIT-FAILED` とする。

### 15.7 エラー処理関数

組み込みライブラリとして、少なくとも次の関数を提供する。

- `recover`: `Function<Function<T>, Function<Error, T>, T>`
- `fail`: `Function<Error, T>`
- `error`: `Function<Number, String, Error>`

`Error` 型:

- `Error` は組み込みの型エイリアス `Record<code: Number, message: String>` である（6.9）。ユーザー定義で上書きしてはならない。

意味論:

- `recover` / `fail` は 6.9, 8.10 の規則に従う。いずれもコア関数であり、ユーザーコードから上書きしてはならない（7.2）。
- `error(code, message)` は `{code: code, message: message}` と同値の `Error` 値を構築する補助関数である。
- `fail` の戻り型 `T` は組み込み多相（4.4）により文脈の期待型から具体化する。

失敗規則:

- `fail` は与えられた `Error` 値を持つ失敗を送出する。未捕捉の場合、プロセスは `code` を終了コードとして終了する（8.10, 11.3）。

### 15.8 シリアル化・型移行補助関数

組み込みライブラリとして、少なくとも次の関数を提供する。

- `toJson`: `Function<Any, String>`
- `fromJson`: `Function<String, Any>`
- `encode`: `Function<Any, String, String>`
- `decode`: `Function<String, String, Any>`
- `cast`: `Function<Any, T>`

形式引数:

- `encode`/`decode` の第 2 引数は format 指定文字列とし、少なくとも `json` と `pretty-json` を受け付ける。

`fromJson` / `decode` の JSON 変換規則:

- JSON number -> `Number`
- JSON string -> `String`
- JSON boolean -> `Bool`
- JSON null -> `Null`
- JSON array -> 配列値（要素は本規則を再帰適用）
- JSON object -> `Record<...>` または `Map<Any>`（実装選択。ただし同一実装内で一貫しなければならない）
- タグ付きメタデータ表現（`$type` フィールドを持つオブジェクト）も特別扱いせず、上記規則で通常のオブジェクトとして変換する。`Void`・`Environment`・`FunctionRef` の復元は行わない（13.1 の往復規則）。

`cast` による型移行:

- `cast(v)` は、値 `v` が対象型 `T` に実行時に適合するかを検査し、適合する場合は `v` を型 `T` の値として返す。`Any` から具体型への唯一の移行手段である（4.4）。
- 対象型 `T` は組み込み多相（4.4）により、参照位置の期待型から一意に具体化されなければならない（例: `user: Record<name: String> = cast(fromJson(stdin))`）。
- 対象型 `T` はデータ型（`Number`、`String`、`Bool`、`Null`、`Environment`、`Any`、およびそれらからなる `Array`/`Map`/`Record`）に限る。`Void`・`Function`・`AsyncHandle` を含む型への `cast` は静的エラー（`E-TYPE-ILLFORMED`）とする。

`cast` の実行時型検査規則:

- 基本型: 実行時値の種別が対象型と一致すること。
- `Array<T>`: 配列値であり、すべての要素が `T` に実行時適合すること。
- `Map<T>`: すべての値が `T` に実行時適合すること。
- `Record<...>`: キー集合が対象型のフィールド集合と一致し、各値が対応するフィールド型に実行時適合すること。
- レコード値とマップ値は相互に許容する。構造条件を満たす場合、実装は必要に応じて対象型の表現（レコードまたはマップ）へ変換する（`fromJson` の JSON object の実装選択を吸収するため）。
- 対象型中の `Any` の位置は無検査で通す。
- 検査に失敗した場合は実行時エラー（`E-RUNTIME-CAST`）とする。診断には失敗した位置（フィールドパス・添字）を含めることが望ましい。

契約:

- 13 章のシリアル化規約に従う。
- 不正 JSON は `E-IO-DATA-DECODE` として報告する。
- 非対応形式指定は `E-CLI-USAGE` または `E-IO-DATA-DECODE` のいずれかで一貫して報告する。

### 15.9 エラー契約

組み込みライブラリの関数は、14 章のエラー体系と整合しなければならない。

最低要件:

- 各失敗パスで `code` と `message` を持つ診断を生成する。
- 可能な場合は `location` と `traceId` を付与する。
- 同一条件に対して同一エラーコードを返す決定性を保つ。

## 16. 例

本章では、仕様全体を横断する代表例を示す。各例は、コードを実行ディレクトリの `main.lask` に置いた前提で、実行コマンドと期待される挙動を併記する。`run` は評価結果を stdout へ出力しない（11.3）ため、値の確認には `eval` を用いる。出力例は既定の `json` 表示である。

### 16.1 最小プログラム

最小構成のモジュール例を示す。

```lask
hello() = "hello, lask"
```

このモジュールは、引数なし関数 `hello` を 1 つ公開し、戻り値 `String` を返す。

実行コマンドと期待される挙動:

```text
$ lask eval hello
"hello, lask"

$ lask run hello
```

- `eval` は評価結果を stdout へ出力し、終了コード `0` で終了する。
- `run` は関数を実行するが、評価結果を stdout へ出力しない（実行ログは stderr）。終了コード `0` で終了する。

### 16.2 型注釈付き関数

型注釈付き関数と既定引数の例を示す。

```lask
greet(name: String, --prefix: String = "hello"): String =
  concat(prefix, concat(", ", name))

add(x: Number, y: Number): Number =
  x + y
```

`greet("alice")` は `"hello, alice"` を返し、`greet("alice", prefix = "hi")` は `"hi, alice"` を返す。

実行コマンドと期待される挙動:

```text
$ lask eval greet alice
"hello, alice"

$ lask eval greet alice --prefix hi
"hi, alice"

$ lask eval add 1 2
3

$ lask run greet alice --prefix hi
```

- `name` は位置パラメータであり、位置でのみ束縛される。`--name alice` のような名前指定はできない（`E-TYPE-KEYWORD` に対応する CLI 使用エラー）。
- `prefix` はキーワードパラメータであり、名前でのみ束縛される。未指定時は既定値 `"hello"` で補完される（7.5）。
- `add` の引数は、既定の `--arg-decode auto` により `1`・`2` が `Number` として位置束縛される。
- 最後の `run` の例は `eval` と同一の構文・束縛で実行されるが、評価結果は stdout へ出力されず、終了コード `0` で終了する。
- 位置パラメータ `name` を与えない `lask run greet` は、実行前エラーとなり関数は評価されない（CLI 使用エラー。終了コード `4`。11.3）。

### 16.3 高階関数と合成

高階関数、パイプ演算子、合成演算子の例を示す。

```lask
applyTwice(f: Function<Number, Number>, x: Number): Number =
  f(f(x))

inc(x: Number): Number = x + 1
double(x: Number): Number = x * 2

pipeline(n: Number): Number =
  n
  |> inc
  |> double

incThenDouble: Function<Number, Number> =
  inc >> double
```

`pipeline(3)` と `incThenDouble(3)` はどちらも `8` を返す。

実行コマンドと期待される挙動:

```text
$ lask eval pipeline 3
8

$ lask eval incThenDouble 3
8
```

- `incThenDouble` は関数値のトップレベル宣言であり、関数宣言と同様に CLI から起動できる。関数型の値としての適用となるため、束縛は位置引数のみである（7.5）。
- `applyTwice` は関数型のパラメータを持つため、CLI からは直接起動できない（いずれのデコード方式でも関数値を構成できず、型不一致の実行前エラーとなる）。言語内から `applyTwice(inc, 3)` と呼び出すと `5` を返す。

### 16.4 配列・マップ・レコード

配列・マップ・レコード値と、組み込みライブラリの関数およびアクセサ式（6.8）の利用例を示す。

```lask
labels(xs: Array<String>): Array<String> =
  map(xs, \(x: String) -> concat("item:", x))

firstLabel(xs: Array<String>): String =
  labels(xs)[0]

user: Record<name: String, age: Number> =
  {name: "alice", age: 20}

userName(): String = user.name

cfg: Record<env: Environment, retries: Number> =
  {env: #alpine:3.20, retries: 3}

retryCount(): Number = cfg.retries

envMap: Map<String> =
  {"APP_ENV": "prod", "REGION": "ap-northeast-1"}

appEnv(): String = envMap["APP_ENV"]

region(): String =
  get(envMap, "REGION")
```

実行コマンドと期待される挙動:

```text
$ lask eval labels '["a", "b"]'
["item:a", "item:b"]

$ lask eval firstLabel '["a", "b"]'
"item:a"

$ lask eval userName
"alice"

$ lask eval retryCount
3

$ lask eval appEnv
"prod"

$ lask eval region
"ap-northeast-1"
```

- `labels` の引数は、既定の `--arg-decode auto` により JSON 配列として解釈され、`Array<String>` へ束縛される。
- `user.name`・`cfg.retries` はレコードのフィールドアクセスである（`.` は `Record` 専用。6.8）。存在しないフィールドの参照は静的エラー（`E-TYPE-ACCESS`）となる。
- `labels(xs)[0]` は配列の添字アクセスである（0 始まり）。範囲外の添字は実行時エラー（`E-RUNTIME-ACCESS`。8.9）となる。
- `envMap["APP_ENV"]` はマップの添字アクセスであり、`get(envMap, "APP_ENV")` と同一の失敗契約を持つ（キー不在は `E-RUNTIME-ACCESS`）。`region` は同じ取得を組み込みライブラリの `get` で行う形である。
- `user`・`cfg`・`envMap` は関数ではない値宣言であり、CLI からの直接起動対象ではない。

### 16.5 手続的記述と環境付きコマンド実行

`do`、`if`、`for` と `$[env] ...` の例を示す。

```lask
buildAndTest(env: Environment): String = do {
  buildOut = $ sh -lc "echo local-build"

  testOut = if (length(buildOut) > 0) {
    $[env] sh -lc "echo container-test"
  } else {
    "skip"
  }

  lines = for (x : ["lint", "unit", "e2e"]) {
    concat("phase:", x)
  }

  concat(join(lines, ","), concat(":", trim(testOut)))
}

ci(): String = buildAndTest(#alpine:3.20)
```

実行コマンドと期待される挙動:

```text
$ lask run ci

$ lask eval ci
"phase:lint,phase:unit,phase:e2e:container-test"
```

- どちらの場合も、ローカルで `echo local-build` が実行され、続いて `alpine:3.20` コンテナ内で `echo container-test` が実行される。`run` は評価結果を出力せず、`eval` は戻り値を stdout へ出力する。
- `buildAndTest` は `Environment` 型のパラメータを持つため CLI 直接起動の対象外である（11.2）。`ci` のように環境を確定させた関数を経由して起動する。
- いずれかのコマンドが非 0 終了した場合は失敗が伝播し、`lask` はそのコマンドの終了コードで終了する（8.10, 11.3）。

実行中、stderr には次のようなコマンド実行ログがリアルタイムに流れる（12.3）:

```text
2026-07-23T10:15:04.101Z [#local:1] $ sh -lc "echo local-build"
2026-07-23T10:15:04.113Z [#local:1] 1| local-build
2026-07-23T10:15:04.114Z [#local:1] exit 0
2026-07-23T10:15:04.360Z [#alpine:3.20:2] $ sh -lc "echo container-test"
2026-07-23T10:15:04.372Z [#alpine:3.20:2] 1| container-test
2026-07-23T10:15:04.373Z [#alpine:3.20:2] exit 0
```

### 16.6 非同期実行

`async`（糖衣）および `spawn`/`await`（コア関数）に対応する例を示す。

```lask
fetchA(): String = $ sh -lc "echo A"
fetchB(): String = $ sh -lc "echo B"

mergeAB(): String = do {
  a = async fetchA()
  b = async fetchB()
  concat(trim(await a), trim(await b))
}
```

この例は意味論上、`spawn(\() -> fetchA())`、`spawn(\() -> fetchB())`、およびコア関数適用 `await(...)` へ正規化される。

実行コマンドと期待される挙動:

```text
$ lask eval mergeAB
"AB"
```

- `fetchA` と `fetchB` は `async` により並行に開始され、`await` で両方の完了を待ってから連結する。2 つのコマンドの完了順序に関わらず、結果は常に `"AB"` である。
- いずれかの非同期タスクが失敗した場合、対応する `await` の時点で失敗が再送出される（8.6）。

### 16.7 CLI 実行例

```text
# 型検証
lask check --module app/main.lask

# ローカル実行（main.lask が既定対象。結果は stdout へ出力されない）
lask run hello
lask run --module app/main.lask hello

# 関数評価（評価結果を stdout へ出力）
lask eval greet alice

# キーワード引数付き実行（greet(name: String, prefix: String = "hello")）
lask run greet alice --prefix hi

# 固定イメージ実行（build は関数内で $[#alpine:3.20] を指定）
lask run --module ci/main.lask build

# リモート環境での実行（provision は #env("ansible") を参照。環境定義は environments.lask.json）
lask run --module ops/main.lask \
  --ssh-known-hosts ~/.ssh/known_hosts \
  --ssh-strict-host-key-checking yes \
  --ssh-connect-timeout 10 \
  provision

# 利用環境の列挙とアクセス検査
lask envs provision --check
```

期待される挙動:

- `lask check`: 診断結果を stdout へ出力する。静的エラーがなければ終了コード `0`、あれば `1`。
- `lask run hello`: 関数を実行し、評価結果は stdout へ出力せず終了コード `0` で終了する。
- `lask eval greet alice`: `"hello, alice"` を stdout へ出力する（既定の `json` 表示）。
- `lask run greet alice --prefix hi`: 位置引数 `alice` とキーワード引数 `--prefix hi` が束縛されて実行される。評価結果は出力されない。
- `build`: コンテナ内でビルドを実行する（評価結果は出力されない）。Docker デーモンへ接続できない場合は実行前エラーとなり、終了コード `3` で終了する。
- `provision`: `environments.lask.json` の `ansible` エントリへ解決し、SSH 接続の上でコマンドを実行する。接続に失敗した場合は `E-IO-SSH-CONNECT` の診断を stderr へ出力し、終了コード `3` で終了する。
- `lask envs provision --check`: `provision` が利用する環境を列挙し、到達性を検査する。すべて到達可能なら終了コード `0`、到達不能な環境があれば `3` とする（11.4）。

環境付きコマンド実行（`runCommand`）を伴う失敗時のイベント出力例を示す。次は、`lask run deploy prod` の実行中に SSH 接続がタイムアウトした場合に発行される `FailEvent` である。

### 16.9 エラー処理と終了コード

`try` / `catch` / `finally` と、終了コード・標準エラーの引き継ぎの例を示す。

```lask
release(): String = do {
  out = try {
    $ ./release.sh
  } catch (e) {
    if (e.code == 75) {
      "retry-later"
    } else {
      fail(e)
    }
  } finally {
    $ rm -rf ./tmp
  }
  out
}
```

実行コマンドと期待される挙動:

```text
$ lask run release
```

- 成功時は終了コード `0` で終了する（戻り値は stdout へ出力されない。値を確認する場合は `lask eval release` を用いる）。`finally` ブロックにより `./tmp` は削除済みである。
- `./release.sh` が終了コード `75` で失敗した場合は捕捉され、`"retry-later"` を返して正常終了する（プロセス終了コード `0`）。
- それ以外の失敗は `fail(e)` で再送出される。未捕捉のままトップレベルへ到達すると、`lask` プロセスはそのコマンドの終了コードで終了し、`e.message`（コマンドの標準エラー出力）が診断として出力される（8.10, 11.3）。
- `finally` ブロックは、成功・捕捉・再送出のいずれの経路でも正確に 1 回評価される。
